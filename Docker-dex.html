Unit 1: Foundations

What Docker is, what a container really is inside the Linux kernel, how the pieces talk to each other, and getting it installed properly.

Definition
Docker is a platform for packaging an application together with everything it needs to run (runtime, libraries, system tools, config) into an image, and running that image as an isolated process called a container.

The problem it solves

Before containers, shipping software meant shipping instructions: "install Python 3.11, then libpq 15, set these env vars, make sure port 5432 is free". Every laptop, CI runner and server drifted a little. The result was the classic works on my machine bug, slow onboarding, and fragile deployments.

Docker replaces the instructions with the artifact itself. You build the environment once, freeze it into an image, and run the same bytes everywhere.

Image

  • A read-only, layered filesystem snapshot plus metadata (default command, env vars, exposed ports, user).
  • Built from a Dockerfile. Stored in a registry like Docker Hub or GHCR.
  • Think of it as a class, or a frozen template.

Container

  • A running (or stopped) instance of an image: the image layers plus a thin writable layer on top, wrapped in kernel isolation.
  • You can start many containers from one image. Each gets its own filesystem view, network stack and process tree.
  • Think of it as an object created from that class.
AnalogyAn image is a shipping container that has been packed and sealed at the factory. A container is that box sitting on a ship, crane or truck. The crane does not care what is inside; it only knows the standard shape. Docker gives software the standard shape.

What you actually get

  • Reproducibility: same image digest, same filesystem, every time.
  • Isolation: two apps needing different versions of OpenSSL or Node live side by side without conflict.
  • Speed: containers start in milliseconds because they are just processes. No guest OS to boot.
  • Density: dozens of containers on a laptop, hundreds on a server.
  • A common unit for the whole pipeline: developers, CI, staging and production all run the same image. Kubernetes, ECS, Cloud Run, Fly.io and Nomad all consume OCI images.
GotchaDocker is not a security sandbox like a VM. Containers share the host kernel. A kernel exploit or a badly configured container (privileged, Docker socket mounted, running as root) can reach the host. Unit 9 covers hardening.

The honest definition
A container is a normal Linux process that the kernel lies to. Namespaces control what it can see, cgroups control how much it can use, and a layered filesystem gives it its own root directory.

2. cgroups: how much it can use

Control groups limit and account for CPU, memory, block I/O and number of processes. When you run docker run --memory 512m --cpus 1.5, Docker writes those numbers into the container's cgroup. Modern distros use cgroup v2 (a single unified hierarchy).

  • Go over the memory limit and the kernel OOM killer kills the process (exit code 137).
  • Go over the CPU quota and you get throttled, not killed.
  • docker stats reads these cgroup counters.

3. Union filesystem (overlay2): the layered root

Each Dockerfile instruction that changes files produces a read-only layer. The overlay2 storage driver stacks these layers (lowerdirs) and adds one writable layer (upperdir) per container. Reads fall through to the first layer that has the file. Writes use copy-on-write: the file is copied up into the writable layer first, then modified.

Why layers matter

  • Pulling a new version of your app downloads only the changed layers.
  • Ten containers from the same image use the disk space of one image plus ten tiny writable layers.
  • Build cache works per layer, which is why Dockerfile ordering matters (Unit 4).

Why the writable layer is not storage

  • It is deleted with the container (docker rm).
  • Copy-on-write is slow for heavy writes (databases).
  • Use volumes for anything you want to keep (Unit 5).

4. The extra security layers

  • Capabilities: root's powers split into ~40 pieces (NET_ADMIN, SYS_ADMIN...). Docker drops most by default.
  • seccomp: a syscall filter. Docker's default profile blocks around 44 dangerous syscalls such as kexec_load and mount.
  • AppArmor / SELinux: mandatory access control profiles applied to the container process.

5. OCI: the standards underneath

The Open Container Initiative defines three specs so images and runtimes from different vendors interoperate:

  • Image spec: how layers, config and manifests are laid out. A Docker-built image runs on Podman, containerd, CRI-O and Kubernetes.
  • Runtime spec: how to run a container from an unpacked bundle. runc is the reference implementation.
  • Distribution spec: the HTTP API registries speak for push and pull.

Rootless mode

The daemon and containers run as your normal user inside a user namespace. A container breakout lands as you, not root. Trade-offs: no binding to ports below 1024 by default, some storage and network drivers are limited, cgroup limits need systemd user delegation.


sudo apt-get install -y uidmap docker-ce-rootless-extras
dockerd-rootless-setuptool.sh install
systemctl --user enable --now docker
export DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock   # add to ~/.bashrc
docker context use rootless

  • No registry given? Docker assumes docker.io.
  • No namespace on Docker Hub? It is an official image under library/.
  • No tag? Docker assumes :latest.

Tags are mutable

A tag is a pointer that can be moved. postgres:16 today is not the same bytes as postgres:16 next month after a patch release. Good for getting security fixes, bad for reproducibility.

Digests are immutable

A digest is the SHA-256 of the manifest. Pinning image@sha256:... guarantees the exact same image forever. Use digests in production manifests and let a bot (Renovate, Dependabot) bump them.

Gotcha: latestlatest is just a default tag name. It does not mean newest, and it is not updated automatically on your machine. docker run nginx uses whatever nginx:latest you pulled months ago. Never deploy latest.

What is inside an image

  • Layers: compressed tarballs of filesystem changes, each addressed by digest.
  • Config: JSON with env vars, entrypoint, cmd, working dir, user, exposed ports, labels, layer history.
  • Manifest: JSON listing the config digest and layer digests for one platform.
  • Index (manifest list): points to several manifests, one per platform (linux/amd64, linux/arm64, linux/arm/v7...). Docker picks the one matching your machine.

docker buildx imagetools inspect nginx:1.27-alpine
docker manifest inspect --verbose redis:7-alpine | jq '.[].Descriptor.platform'
Gotcha: Apple silicon and arm64An image built on an M-series Mac is linux/arm64. Push it and run it on an x86 server and you get exec format error. Build with --platform linux/amd64 or build multi-platform with buildx (Unit 4).

exec vs attach

docker exec

Starts a new process next to your app. Exiting it does not affect the container. This is what you want 99% of the time.

docker attach

Connects to the existing PID 1. Ctrl-C sends SIGINT to your app and usually stops the container. Detach safely with Ctrl-P Ctrl-Q (only works if started with -it).

Gotcha: logs only see PID 1docker logs shows what the main process writes to stdout/stderr. If your app writes to /var/log/app.log instead, logs look empty. Configure apps to log to stdout, or symlink the file to /dev/stdout like the official nginx image does.

PID 1 is special

  • The kernel does not apply default signal handlers to PID 1. If your app does not explicitly handle SIGTERM, docker stop waits the full 10 seconds and then SIGKILLs it. Slow shutdowns are usually this.
  • PID 1 must reap orphaned child processes. Most apps do not, so zombies accumulate in containers that spawn subprocesses.
  • If you use the shell form (CMD python app.py), PID 1 is /bin/sh -c, which does not forward signals to Python.

Fixes: use exec form (CMD ["python", "app.py"]), use exec "$@" at the end of entrypoint scripts, and add --init (or init: true in Compose) to get tini as PID 1.


docker run -d --name slow alpine sh -c 'sleep 1000'

docker rm slow
docker run -d --init --name fast alpine sh -c 'sleep 1000'
time docker stop fast          # well under a second: tini forwards the signal
docker rm fast

Docker uses an increasing back-off between restarts (starting at 100 ms and doubling) so a crash loop does not melt the host. The policy only kicks in after the container has been up for at least 10 seconds once.

Without limits a container can use all of the host's memory and CPU. One leaky service can take down everything on the box. Always set memory limits in production.

Memory

  • -m 512m: hard ceiling. Exceed it and the kernel kills a process (usually your app), exit 137, OOMKilled=true.
  • --memory-reservation: soft target the kernel reclaims towards when the host is under pressure.
  • --memory-swap: total memory + swap. -1 unlimited swap. Equal to -m means no swap.
  • Runtimes like the JVM and Node read the cgroup limit in modern versions, but set -Xmx or --max-old-space-size explicitly anyway.

CPU

  • --cpus 2: at most two cores' worth of CPU time per period. Over it you are throttled.
  • --cpu-shares: only matters when CPUs are busy; a container with 2048 gets twice the time of one with 1024.
  • --cpuset-cpus 0-3: restrict to cores 0 to 3 (NUMA tuning, noisy neighbours).
  • nproc inside a container still shows all host cores. Tell your app the worker count explicitly.

Cache rule
Each instruction is cached by its text plus its inputs (for COPY/ADD, the checksums of the files). The moment one step misses the cache, every step after it is rebuilt.

Slow: code copied before dependencies


FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]

Editing one line of server.js reinstalls every package.

Fast: dependencies first


FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY . .
CMD ["node", "server.js"]

Code edits only redo the last COPY. npm ci reruns only when the lockfile changes.

Ordering rules

  1. Things that change rarely go first: base image, system packages, language runtime.
  2. Then dependency manifests (requirements.txt, package-lock.json, go.sum, Cargo.lock) and the install step.
  3. Then your source code.
  4. Metadata (LABEL, EXPOSE, CMD) last; they are cheap but keep them near the end for clarity.

Keeping images small

  • Install and clean in the same RUN. Deleting files in a later layer does not shrink the image; the bytes stay in the earlier layer.
  • apt-get install --no-install-recommends then rm -rf /var/lib/apt/lists/*. On Alpine: apk add --no-cache.
  • pip install --no-cache-dir (or a cache mount, which is better), npm ci --omit=dev, npm cache clean --force.
  • Use multi-stage builds so compilers and dev dependencies never reach the final image.
  • Pick a smaller base: -slim, -alpine, distroless, or scratch for static binaries.
  • Check with docker images, docker history and dive.

# wrong: the 200 MB of build deps still exist in the first layer
RUN apt-get update && apt-get install -y build-essential
RUN pip install -r requirements.txt
RUN apt-get purge -y build-essential

# right: one layer, nothing left behind
RUN apt-get update \
 && apt-get install -y --no-install-recommends build-essential \
 && pip install --no-cache-dir -r requirements.txt \
 && apt-get purge -y build-essential && apt-get autoremove -y \
 && rm -rf /var/lib/apt/lists/*

Cache busters to know about

  • COPY . . with no .dockerignore: any file change, including .git, busts it.
  • Changing a --build-arg value busts every step that uses that ARG (and steps after them).
  • ADD https://... re-downloads to check for changes.
  • Base image updated with --pull: everything rebuilds (which is what you want for security patches).

Best practice checklist

  1. Start with # syntax=docker/dockerfile:1.
  2. Pin base image versions (and ideally digests). Never latest.
  3. Add a .dockerignore.
  4. Order layers from least to most frequently changing.
  5. Use multi-stage builds; the final stage contains only runtime needs.
  6. Combine install and cleanup in one RUN; use cache mounts for package managers.
  7. Run as a non-root user with a fixed numeric UID.
  8. Use exec form for CMD and ENTRYPOINT; exec "$@" in wrapper scripts.
  9. One main process per container. Use Compose for the rest.
  10. Never bake secrets into layers (no COPY .env, no secret ARGs).
  11. Add a HEALTHCHECK, or define one in Compose.
  12. Add OCI labels (org.opencontainers.image.source, version, revision).
  13. Log to stdout/stderr.
  14. Make images configurable through env vars, not rebuilds per environment. Build once, promote the same image.
  15. Scan images (docker scout cves, Trivy, Grype) and rebuild regularly for base patches.

Copy-up: volumes get the image's files

When an empty volume is mounted over a directory that has content in the image, Docker copies that content into the volume first. Bind mounts never do this; they hide whatever the image had at that path. This is why mounting ./html over /usr/share/nginx/html shows your folder, while a fresh named volume there shows nginx's default page.

The UID problem

Linux permissions use numbers, not names. A file created by root (UID 0) in a container is owned by root on the host. A container running as UID 10001 cannot write to a host folder owned by your user (UID 1000).

  • Run as your user: -u "$(id -u):$(id -g)" for tool containers that write into your project.
  • Match UIDs at build: ARG UID=1000 then useradd -u $UID app.
  • Fix ownership once for a data dir: sudo chown -R 10001:10001 ./data.
  • Prefer named volumes for data the app writes; Docker handles them and copy-up keeps image ownership.
  • Docker Desktop on Mac and Windows maps ownership for you, which hides this problem until you deploy to Linux.

SELinux hosts (Fedora, RHEL)

Add :z (shared label) or :Z (private label) so the container can read the path: -v ./data:/data:Z. Never :Z on /home or /usr; it relabels them.

Mount propagation

bind-propagation=rprivate (default), rshared, rslave... Only matters when mounts are created inside the mounted tree after start, e.g. tools that mount filesystems.

Gotcha: mounting over node_modulesMounting .:/app in a Node project hides the node_modules that npm ci installed in the image. The fix is an extra anonymous volume for that path so it is not shadowed: -v .:/app -v /app/node_modules. Compose watch avoids this entirely (Unit 7).

Lives in RAM, never touches disk, limited by size. Great with --read-only for apps that need a writable scratch dir, and for files you do not want persisted.

EXPOSE does not publish

EXPOSE 8000 is documentation plus a hint for -P. Containers on the same network can reach each other on any port regardless of EXPOSE. Only -p opens a port to the outside.

Container must listen on 0.0.0.0

An app that listens on 127.0.0.1 inside the container is unreachable from outside it, even with -p. Start dev servers with --host 0.0.0.0. This is the most common "port published but connection refused" cause.

Container DNS

  • On user-defined networks, containers use Docker's embedded DNS at 127.0.0.11. It answers container names, aliases and Compose service names, and forwards everything else to the host's resolvers.
  • Override with --dns 1.1.1.1, --dns-search corp.local, --dns-option ndots:1, or daemon-wide in daemon.json.
  • On the default bridge, /etc/resolv.conf is copied from the host (minus localhost entries).

Talking to services on the host

  • Docker Desktop: host.docker.internal resolves to the host automatically.
  • Linux: add it yourself: --add-host host.docker.internal:host-gateway (or extra_hosts in Compose). The host service must listen on an address reachable from the bridge, not only 127.0.0.1.
  • localhost inside a container means the container itself, never the host.
  • --network host on Linux makes localhost the host, at the cost of isolation.

docker run --rm --add-host host.docker.internal:host-gateway curlimages/curl \
  -s http://host.docker.internal:3000/health

Define a whole application (services, networks, volumes, secrets) in one YAML file. The full file reference, variables and env files, startup order with health checks, profiles, overrides, watch mode and every command.

Definition
Docker Compose reads a YAML file describing services and turns it into containers, networks and volumes with one command: docker compose up. Everything you could do with long docker run commands, but declarative and in version control.

Compose v2 (current)

  • A Docker CLI plugin: docker compose (space).
  • Default file names, in order: compose.yaml, compose.yml, docker-compose.yaml, docker-compose.yml.
  • Follows the Compose Specification. The top-level version: key is obsolete and ignored; delete it.

Compose v1 (dead)

  • The old Python tool docker-compose (hyphen). End of life since 2023.
  • Container names used _ (app_web_1); v2 uses - (app-web-1).
  • If a tutorial says docker-compose, just type docker compose.

Override files and merging

  • With no -f, Compose reads compose.yaml and compose.override.yaml automatically. Put dev-only settings in the override.
  • With -f, only the files you name are read, merged left to right: docker compose -f compose.yaml -f compose.prod.yaml up -d. The override file is not loaded.
  • Merge rules: single values (image, command) are replaced; maps (environment, labels) are merged by key; lists like ports and volumes are combined (volumes and ports de-duplicated by target).
  • Use !reset to clear a value from a base file and !override to replace a list instead of merging.
  • COMPOSE_FILE=compose.yaml:compose.prod.yaml in the environment saves typing.

Unit 9: Security and Hardening

The threat model, non-root users, capabilities, seccomp and AppArmor, read-only filesystems, rootless and user namespaces, secrets handling, and a hardening checklist.

  1. Vulnerable image contents: outdated OpenSSL, glibc, your own dependencies. Fixed by small images, scanning and regular rebuilds.
  2. Leaked secrets: API keys in layers, ENV, logs or git. Fixed by build secrets, runtime secrets and .dockerignore.
  3. Container escape: kernel bugs, privileged containers, mounted Docker socket, dangerous capabilities. Fixed by least privilege and keeping the host patched.
  4. Lateral movement: one compromised container reaching databases it should not. Fixed by network segmentation and internal networks.
  5. Resource exhaustion: fork bombs, memory leaks taking down the host. Fixed by cgroup limits.
  6. Untrusted images: typosquatted or malicious images. Fixed by official/verified sources, pinning digests, signature verification.
The big three to never do--privileged, mounting /var/run/docker.sock, and mounting the host root (-v /:/host) each hand over the whole host. If a tool's README asks for one of these, understand exactly why first.

By default the process in a container runs as root (UID 0). It is restricted by namespaces and dropped capabilities, but if it escapes, it is root on the host (unless user namespaces are on). Running as an unprivileged user removes most of the risk for free.


# Debian / Ubuntu based
RUN groupadd --system --gid 10001 app \
 && useradd --system --uid 10001 --gid app --home-dir /app --shell /usr/sbin/nologin app

# Alpine
RUN addgroup -S -g 10001 app && adduser -S -u 10001 -G app app

# distroless already ships a "nonroot" user (65532)

  • Non-root processes cannot bind ports below 1024. Listen on 8080 and publish -p 80:8080, or add only NET_BIND_SERVICE.
  • Override at runtime with docker run -u 10001:10001 or user: in Compose.
  • Check: docker exec api id should not print uid=0.

seccomp and AppArmor

  • The default seccomp profile blocks dangerous syscalls. Never run --security-opt seccomp=unconfined in production.
  • Custom profile: --security-opt seccomp=./profile.json. Generate one by tracing your app.
  • On Ubuntu/Debian, Docker applies the docker-default AppArmor profile. Custom: --security-opt apparmor=myprofile. SELinux hosts use labels instead.

no-new-privileges

--security-opt no-new-privileges:true stops processes from gaining privileges through setuid/setgid binaries (like su, sudo, ping on old systems). Turn it on everywhere; set it daemon-wide with "no-new-privileges": true in daemon.json.

Read-only root filesystem

An attacker who gets code execution cannot drop binaries or modify your app. Give the app writable tmpfs or volumes only where it needs them (/tmp, caches, upload dirs).

Runtime

  • --cap-drop ALL, add back individually.

Host

  • Firewall with DOCKER-USER chain awareness.
  • Separate hosts or VMs for workloads of different trust levels.

Unit 11: Orchestration

When one host is not enough. Docker Swarm end to end with every command, then how everything you learned maps onto Kubernetes.

Compose runs containers on a single Docker host. An orchestrator manages a cluster of hosts and adds:

  • Scheduling: decides which node runs each container based on resources and constraints.
  • Self-healing: replaces failed containers and reschedules work when a node dies.
  • Desired state: you declare "3 replicas of api:1.4.2"; it continuously makes reality match.
  • Rolling updates and rollbacks with health gating.
  • Service discovery and load balancing across nodes.
  • Secrets and config distribution to the right nodes, encrypted.

Hosts1ManyMany

@app.post("/api/links", status_code=201)
def create_link(body: LinkIn):
    target = str(body.url)
    for _ in range(5):
        code = new_code()
        with pool.connection() as conn:
            row = conn.execute(
                "INSERT INTO links (code, target) VALUES (%s, %s) "
                "ON CONFLICT (code) DO NOTHING RETURNING code",
                (code, target),
            ).fetchone()
        if row:
            cache.set(f"link:{code}", target, ex=CACHE_TTL)
            return {"code": code, "short_url": f"{settings.public_url}/{code}"}
    raise HTTPException(503, "could not allocate a code, try again")


@app.get("/api/links/{code}")

    with pool.connection() as conn:
        row = conn.execute(
            "SELECT target, created_at FROM links WHERE code = %s", (code,)

        raise HTTPException(404, "unknown code")
    hits = int(cache.get(f"hits:{code}") or 0)

Why each choice

  • slim base: glibc, so psycopg[binary] and uvloop install as prebuilt wheels in seconds.
  • bind mount for requirements: the file is used without becoming a layer; changes to it still bust the cache correctly.
  • cache mount: pip's download cache survives between builds but never lands in the image.
  • test stage: tests run in the exact dependency set that ships, but pytest is not in the final image.
  • --chown=app:app: lets Compose watch sync files into /app/app later, because the non-root user owns that directory.
  • healthcheck in exec form with Python: slim has no curl, and Python is already there.
  • exec-form CMD: uvicorn is PID 1 and shuts down cleanly on SIGTERM.

IMPWhat is the difference between an image and a container?

An image is a read-only, layered template (filesystem + config). A container is a runtime instance of an image: the image layers plus a writable layer, running as an isolated process with its own namespaces and cgroup limits. Many containers can run from one image.

IMPHow is a container different from a virtual machine?

A VM virtualizes hardware and runs a full guest OS with its own kernel on a hypervisor. A container is a process on the host kernel isolated with namespaces and limited with cgroups. Containers start in milliseconds and are MBs in size; VMs give stronger isolation and can run a different OS kernel.

IMPWhich Linux features make containers possible?

Namespaces (pid, net, mnt, uts, ipc, user, cgroup) for isolation; cgroups for resource limits and accounting; union filesystems such as overlay2 for layered, copy-on-write images; plus capabilities, seccomp and AppArmor/SELinux for privilege reduction.

IMPCMD vs ENTRYPOINT?

ENTRYPOINT sets the executable; CMD sets default arguments (or the default command if no ENTRYPOINT). Arguments to docker run replace CMD; --entrypoint replaces ENTRYPOINT. Use exec (JSON) form for both so the process is PID 1 and receives signals. Shell-form ENTRYPOINT ignores CMD.

IMPCOPY vs ADD?

Both copy files into the image. ADD can also fetch URLs, clone git repos and auto-extract local tar archives. Prefer COPY for clarity; use ADD only for those extra features (with --checksum for URLs).

IMPARG vs ENV?

ARG exists only at build time and is set with --build-arg; ENV is available at build time after declaration and at runtime, and can be overridden with -e. Neither is safe for secrets: both appear in image history/metadata. Use BuildKit secret mounts.

IMPHow does layer caching work and how do you order a Dockerfile for it?

Each instruction is cached by its text and inputs (file checksums for COPY/ADD). A cache miss invalidates every following step. Put rarely-changing steps first: base image, system packages, dependency manifests and install, then application code last.

IMPWhat are multi-stage builds and why use them?

Several FROM stages in one Dockerfile; only the final (or targeted) stage becomes the image. Build tools and dev dependencies stay in earlier stages and only artifacts are copied forward with COPY --from. Results: smaller, more secure images and a single Dockerfile for build, test and runtime.

IMPVolumes vs bind mounts vs tmpfs?

Volumes are Docker-managed storage under Docker's data dir, best for persistent app data, portable through drivers, pre-populated from the image. Bind mounts map any host path, best for dev source code and config files, tied to the host layout. tmpfs is in-memory, non-persistent, good for scratch data and secrets.

IMPWhy prefer a user-defined bridge network over the default bridge?

User-defined bridges provide automatic DNS resolution by container/service name, better isolation (only attached containers share it), and containers can be connected or disconnected at runtime. The default bridge only allows IP-based communication (or legacy links).

IMPWhat does EXPOSE do? How is it different from -p?

EXPOSE documents which ports the app listens on and is used by -P. It does not publish anything. -p host:container actually maps a host port to the container. Containers on the same network can reach each other's ports regardless of EXPOSE.

IMPWhy does docker stop take 10 seconds for some containers?

docker stop sends SIGTERM and waits (default 10s) before SIGKILL. If PID 1 is a shell (shell-form CMD) or an app without a SIGTERM handler, the signal is ignored because PID 1 has no default handlers. Fix with exec-form CMD, exec "$@" in entrypoints, signal handling in the app, or --init.

IMPWhat does exit code 137 mean?

128 + 9: the process was killed with SIGKILL, most often by the OOM killer after exceeding its memory limit (State.OOMKilled=true), or by docker kill or a stop timeout.

IMPHow do you make a service wait for its database in Compose?

Give the database a healthcheck (e.g. pg_isready) and use depends_on: db: condition: service_healthy. For one-off jobs like migrations, condition: service_completed_successfully. The application should still retry connections at runtime.

What is the build context and what is .dockerignore for?

The build context is the set of files sent to the builder; COPY/ADD can only access them. .dockerignore excludes files from the context, which speeds builds, keeps the cache stable and prevents secrets and junk from entering images.

How do you reduce image size?

Smaller base (slim, alpine, distroless, scratch), multi-stage builds, combining install and cleanup in one RUN, --no-install-recommends, removing package caches or using cache mounts, production-only dependencies, a good .dockerignore, and inspecting layers with docker history or dive.

IMPHow do you secure a Docker container?

Minimal, scanned, pinned images; non-root USER; --cap-drop ALL plus only needed capabilities; no-new-privileges; read-only root filesystem with tmpfs; resource limits; no --privileged or Docker socket mounts; secrets via files or a secret manager, never in layers; internal networks and minimal published ports; patched host and Docker; optionally rootless mode or user namespaces.

What is the difference between docker save/load and export/import?

save/load move images with all layers, tags and metadata. export/import flatten a container's filesystem into a single-layer image without history, CMD or ENV.

What are dangling images?

Images with no tag (<none>:<none>), usually old versions left behind after rebuilding with the same tag. Remove them with docker image prune.

Explain containerd, runc and the shim.

dockerd delegates container lifecycle to containerd (image storage, snapshots, lifecycle). containerd starts a shim per container, which calls runc, the OCI runtime that creates namespaces/cgroups and execs the process, then exits. The shim stays as parent to hold stdio and exit status, allowing daemon restarts without killing containers.

What is a multi-platform image and how do you build one?

An image index pointing to one manifest per OS/architecture; the client pulls the matching one. Build with docker buildx build --platform linux/amd64,linux/arm64 --push, using QEMU emulation or cross-compilation with $BUILDPLATFORM/$TARGETARCH.

Docker Compose vs Docker Swarm vs Kubernetes?

Compose defines and runs multi-container apps on one host. Swarm is Docker's built-in clustering: same Compose-style files deployed as stacks across nodes, with scheduling, rolling updates and secrets. Kubernetes is the industry-standard orchestrator with a much larger feature set and ecosystem, at higher complexity.

How do restart policies differ?

no: never. on-failure[:N]: only on non-zero exit, up to N times. always: always, including on daemon start even if previously stopped manually. unless-stopped: like always but stays stopped after a manual stop.

How does container DNS work?

On user-defined networks each container uses Docker's embedded DNS server at 127.0.0.11, which resolves container names, network aliases and Compose service names to container IPs (multiple IPs for scaled services) and forwards other queries to the host's upstream resolvers.

What is the danger of mounting /var/run/docker.sock into a container?

The container can then call the Docker API with full control: start a privileged container that mounts the host filesystem, effectively becoming root on the host. Only do it for trusted tools, ideally through a filtering socket proxy with read-only permissions.
