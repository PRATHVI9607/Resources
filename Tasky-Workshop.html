The four things in the code that Docker cares about

port: Number(process.env.PORT ?? 3000)config.js: the API listens on port 3000 unless told otherwise. We will publish or proxy this port.
host: process.env.DB_HOST ?? "localhost"Defaults suit a laptop. Inside Docker we set DB_HOST=db, because localhost inside a container is the container itself.
const file = process.env[`${name}_FILE`];If DB_PASSWORD_FILE is set, the password is read from that file. This is how Docker secrets reach the app without appearing in env vars.
app.listen(config.port, "0.0.0.0", ...)server.js: binds to all interfaces. If it bound to 127.0.0.1, nothing outside the container could reach it, even with a published port.
process.on("SIGTERM", shutdown);docker stop sends SIGTERM. The handler finishes open requests and closes the database pool, so stops take well under a second instead of the 10-second kill timeout.
"/api": apiUrlvite.config.js: the dev server forwards /api calls to API_URL. In Docker that becomes http://api:3000.

The rule behind all of it

The same code runs on your laptop, in CI and on the server. Only environment variables and mounted files change. This is the "Twelve-Factor" idea of config, and it is what lets us build one image and run it everywhere.

Image vs container
An image is a read-only template: a filesystem snapshot plus a default command. A container is one running (or stopped) copy of an image, with its own writable layer, network and processes. One image, many containers, like one class and many objects.

COPY package.json package-lock.json ./Copy only the dependency list first. Destination ./ means "into WORKDIR".
RUN npm ci --omit=devRun a command at build time. npm ci installs exactly what the lockfile says; --omit=dev skips dev-only packages.
COPY . .Now copy the rest of the source. Code changes often, so it comes after the slow install step.
EXPOSE 3000Documentation: "this app listens on 3000". It does not publish anything; -p does that.
CMD ["node", "src/server.js"]The default command when a container starts. JSON array = exec form: node becomes PID 1 and receives SIGTERM directly.

8.2 nginx config


server {
    listen 80;
    server_name _;

    root /usr/share/nginx/html;
    index index.html;

    # Docker's built-in DNS server. Putting the upstream in a variable makes
    # nginx look "api" up again every 10s, so new or scaled containers are found.
    resolver 127.0.0.11 valid=10s ipv6=off;
    set $api http://api:3000;

    location /api/ {
        proxy_pass $api;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # hashed build files never change, cache them hard
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    # React router style fallback: unknown paths get index.html
    location / {
        try_files $uri $uri/ /index.html;
    }
}
Anatomy: resolver and proxy_pass
> resolver 127.0.0.11 valid=10s ipv6=off; > set $api http://api:3000; > location /api/ { proxy_pass $api; } resolver 127.0.0.11 :: use Docker's embedded DNS server, which exists in every user-defined network :: kw valid=10s :: cache answers for 10 seconds only :: val ipv6=off :: do not ask for IPv6 addresses :: val set $api http://api:3000 :: store the upstream in a variable :: kw api :: the network alias we gave the API container (and later the Compose service name) :: arg location /api/ :: this block handles every URL that starts with /api/ :: kw proxy_pass $api :: forward the request, full path included, to the API :: kw
Why the variable trickWith a plain proxy_pass http://api:3000; nginx looks up api once at startup, and refuses to start if it does not exist yet. When the API container is replaced and gets a new IP, nginx keeps sending traffic to the old one and you get 502 Bad Gateway. A variable plus resolver makes nginx resolve at request time.

IMPWhy does the api Dockerfile copy package.json before the rest of the code?

Layer caching. The npm ci layer only depends on the two package files, so editing source code reuses the cached install and only reruns the final COPY . ..

IMPThe api container gets ECONNREFUSED 127.0.0.1:5432. Why, and what is the fix?

Inside a container, localhost is the container itself. Put the api and the database on the same user-defined network and set DB_HOST to the database's container or service name.

IMPWhat does condition: service_completed_successfully do for migrate?

The api waits until the migrate container has run and exited with code 0, so it never starts against a database without tables.

IMPWhy are there two Compose files for dev and prod, and how is each loaded?

compose.override.yaml is merged automatically by plain docker compose and adds dev targets, watch and debug tools. Production passes -f compose.yaml -f compose.prod.yaml (or COMPOSE_FILE), which skips the override and adds caddy, hardening and !reset of build sections.

Why is VITE_APP_NAME a build arg, but DB_HOST a runtime env var?

The React bundle is static files in a browser; there is no process to read env vars, so Vite bakes VITE_* values in at build time. The API is a running process that reads its environment on start.

IMPWhat breaks if CMD uses shell form?

/bin/sh becomes PID 1 and does not forward SIGTERM, so docker stop waits 10 seconds and then kills the app (exit 137) mid-request.

Why does nginx.conf put the upstream in a variable?

So nginx resolves api through Docker DNS at request time (every 10 seconds) instead of once at startup. Replaced or scaled api containers are then found without restarting nginx.

What survives docker compose down? And down -v?

down removes containers and networks and keeps volumes, so the data survives. down -v also removes the named volumes: the data is gone.

Why use watch sync instead of bind-mounting the source in dev?

A bind mount over /app hides the image's Linux node_modules, is slow through Desktop file sharing, and can create root-owned files. Sync copies only changed files into the container and works the same on every OS.

How do you roll back a bad release, and what does a rollback not undo?

Set TAG back to the previous version and run docker compose up -d. Database changes are not undone, so migrations must stay compatible with the previous version.

Where would a Kubernetes migration start from here?

The images are already OCI images in a registry. Each Compose service becomes a Deployment plus a Service; volumes become PersistentVolumeClaims, secrets become Secrets, healthchecks become probes, and migrate becomes a Job. Docker-dex Unit 11 maps every key.
