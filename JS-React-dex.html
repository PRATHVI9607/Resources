Unit 1: Start Here

What JavaScript is, where it runs, how to set up a machine that can run it, your first program, and how to read the diagrams in this guide.

JavaScript is a programming language. A program is a text file of instructions, and something has to read those instructions and carry them out. That something is a JavaScript engine. The language and the engine are different things, in the same way a recipe and a cook are different things.

The same language in two places

In this guide you will use both. Node is where you run small experiments and the build tools. The browser is where your apps actually live. When a feature exists in only one of them, the entry says so.

Primitives are copied, objects are shared

This is the single most important idea in this unit. A primitive variable holds the value itself. An object variable holds a reference (think: an address). Copying the variable copies the address, not the object.

let a = 5;
let b = a;      // b gets its own copy of 5
b = 10;
console.log(a, b);   // a is untouched

const p1 = { name: "Asha" };
const p2 = p1;       // p2 points at the SAME object
p2.name = "Ben";
console.log(p1.name); // changed through p2

console.log({} === {});        // two different objects, never equal
console.log(p1 === p2);        // same reference, equal
5 10 Ben false true

This is why React insists on never mutating state: if you change the object in place, the reference stays the same, and React cannot tell anything happened. You will meet this again in the state entries.

null or undefined?A function that finds nothing usually returns undefined (it just did not return anything). When you want to say "this has no value, on purpose", use null. Check for either with value == null or value ?? fallback (both covered in the operators entry).

Naming rules

  • Letters, digits, _ and $. Cannot start with a digit. Case matters: total and Total are different.
  • Cannot be a reserved word (class, function, new...).
  • Convention: camelCase for variables and functions, PascalCase for classes and React components, UPPER_SNAKE for true constants such as PAGE_SIZE.
  • Names should say what the thing is: recipes, isLoading, handleSave. Booleans read well with is, has, can.
Rule of thumbWrite const everywhere. When the linter or the language complains that you re-assign, change that one to let. Reading code is easier when most names never move.

Use === (three equals)

=== compares value and type, with no conversions. == converts types first, with surprising results. Always use === and !==. The one accepted use of == is x == null, which means "is null or undefined".

console.log(5 === 5);        // true
console.log(5 === "5");      // false: number vs string
console.log(5 == "5");       // true:  "5" was converted, avoid this
console.log(0 == false);     // true:  another conversion
console.log(null == undefined);  // true:  the one useful case
console.log(null === undefined); // false
console.log(NaN === NaN);    // false! NaN is never equal to anything
console.log(Number.isNaN(NaN)); // true: the right way to test for NaN
console.log(Object.is(NaN, NaN)); // true: Object.is is === without the NaN quirk

A function is a named, reusable piece of code. You hand it parameters (inputs), it does work, and it hands back a return value (output). In JavaScript functions are values, just like numbers: you can store them in variables, pass them to other functions, and return them. React is built on this idea.

Function declarations are fully ready from the start. var names exist but are undefined until their line runs. let and const names exist but are locked: touching them before their line throws an error. Unit 4: Asynchronous JavaScript

The event loop, timers, callbacks, promises, async and await, fetch, cancelling requests, and the patterns real apps use to stay correct while waiting.

JavaScript runs your code on one thread: it does one thing at a time. Yet pages stay responsive while waiting for the network or a timer. The trick is that waiting is done outside the language (by the browser or Node), and when it finishes, a callback is put in a queue. The event loop moves queued callbacks onto the call stack only when the stack is empty.

Read the output against the diagram: the two console.log calls are plain code, so they run first, in order. Then, with the stack empty, the microtasks run. Only then does the timer callback get its turn, even though its delay was 0.

A long task blocks everything

Because there is one thread, a loop that runs for two seconds freezes the whole page: no clicks, no scrolling, no repaint. Heavy work belongs in a Web Worker, or must be split into chunks.

textContent vs innerHTML (and the reason XSS exists)

textContent puts text on the page exactly as written. innerHTML parses a string as HTML. If that string contains something a user typed, they can inject tags and scripts. This attack is called XSS (cross-site scripting).

const typed = '<img src=x onerror="alert(document.cookie)">';   // what a hostile user might submit

Bubbling and delegation

An event does not just visit the clicked element. It travels down from window to the target (capture phase), then bubbles up through every ancestor to window. Handlers normally run on the way up. This lets one listener on a parent handle clicks from many children: event delegation.

document.querySelector(".list").addEventListener("click", (event) => {
  const button = event.target.closest("button[data-action]");   // which button, if any, was clicked?
  if (!button) return;                                           // click was on something else
  const id = button.closest("li").dataset.id;
  if (button.dataset.action === "delete") removeRecipe(id);
});

With delegation you attach one listener, items added later work automatically, and there are no listeners to clean up per item. React does this internally: it attaches one listener at the root and dispatches to your onClick props.

  • event.target may be a child (an icon inside the button). Use closest() to find what you meant.
  • Custom events: el.dispatchEvent(new CustomEvent("saved", { detail: { id: 3 }, bubbles: true })) lets your own code talk through the DOM.

CORS in plain words

The same-origin policy stops a page on a.com from reading responses from b.com. CORS (Cross-Origin Resource Sharing) is how b.com says "that is fine" by sending Access-Control-Allow-Origin: https://a.com. The check is done by the browser, so it appears only in browser apps. When you see "blocked by CORS policy" the fix is on the server (or a dev proxy), not in your fetch call. The APIs used in this guide (DummyJSON) send permissive CORS headers so that they work from any page.

Rule of thumbTreat every value that came from outside your code (URL, form, storage, API response) as untrusted until validated, and never use it to build HTML, URLs or code as a string.

const BASE = 'https://dummyjson.com/recipes'

export const PAGE_SIZE = 12

async function getJson(url, signal) {
  const res = await fetch(url, { signal })
  // fetch only rejects on network failure, so a 404 or 500 has to be checked by hand
  if (!res.ok) throw new Error(`Request failed (${res.status})`)
  return res.json()
}

export function listRecipes({ query = '', page = 1 } = {}, signal) {
  const skip = (page - 1) * PAGE_SIZE
  const term = query.trim()
  const path = term ? `${BASE}/search?q=${encodeURIComponent(term)}&` : `${BASE}?`
  return getJson(`${path}limit=${PAGE_SIZE}&skip=${skip}`, signal)
}

export function getRecipe(id, signal) {
  return getJson(`${BASE}/${id}`, signal)
}

js/dom.js: building elements without innerHTML

// h('button', { class: 'btn', onclick: fn }, 'Save') builds a real DOM node.
// This is, in spirit, what JSX compiles down to in React.
export function h(tag, props, ...children) {
  const el = document.createElement(tag)

  for (const [key, value] of Object.entries(props ?? {})) {
    if (key.startsWith('on')) el.addEventListener(key.slice(2), value)
    else if (key === 'class') el.className = value
    else if (key in el) el[key] = value // value, disabled, src, href, type ...
    else el.setAttribute(key, value) // aria-*, data-*
  }

  // append() turns strings into text nodes, so user data can never become markup
  el.append(...children.flat().filter((c) => c != null && c !== false))
  return el
}

How dom.js works

  1. document.createElement(tag) makes the element.
  2. Object.entries(props ?? {}) loops over the props. The ?? {} lets callers pass null when there are none.
  3. Key starts with on: key.slice(2) turns onclick into click and registers a listener.
  4. class is mapped to className (class is a reserved word, so the property has another name).
  5. key in el asks "is this a real DOM property?" (disabled, src, href, value). If yes, set the property, which is more reliable than the attribute for live values.
  6. Otherwise setAttribute handles aria-* and data-*.
  7. el.append(...children.flat().filter(...)): flat() lets you pass arrays (from map), the filter drops null and false so you can write cond && h(...).
This is JSX's ancestorIn React you write <button className="btn" onClick={save}>Save</button>. The build tool turns that into a function call very much like h("button", { className: "btn", onClick: save }, "Save"). When you meet JSX in Unit 9, remember it is only this.

Write js/favorites.js

const KEY = 'recipe-box:favorites'

// storage is a parameter so tests can hand in a fake instead of the real localStorage
export function createFavorites(storage = globalThis.localStorage) {
  const listeners = new Set()
  let items = read()

  function read() {
    try {
      return JSON.parse(storage.getItem(KEY)) ?? []
    } catch {
      return []
    }
  }

  function commit(next) {
    items = next
    try {
      storage.setItem(KEY, JSON.stringify(items))
    } catch {
      // private mode or full storage: keep working in memory
    }
    listeners.forEach((fn) => fn(items))
  }

  const has = (id) => items.some((r) => r.id === id)

  return {
    list: () => items,
    has,
    toggle: (recipe) =>
      commit(has(recipe.id) ? items.filter((r) => r.id !== recipe.id) : [...items, recipe]),
    clear: () => commit([]),
    subscribe(fn) {
      listeners.add(fn)
      return () => listeners.delete(fn)
    },
  }
}

The idea: one owner of the data, and a way to be told about changes

Favourites are needed in several places: every card's Save button, the nav counter, the favourites page. If each place kept its own copy they would disagree. So one object owns the list and everyone else asks it. When it changes, it notifies subscribers. This is the observer pattern, and it is the core idea behind Redux, Zustand and React's context-plus-state.

createFavorites(storage)
A factory function. The parameter defaults to the real localStorage, and tests pass a fake. This is dependency injection in one line.
listeners = new Set()
A Set so adding the same function twice does not call it twice, and deleting is easy.
let items = read()
The private state. It lives in the closure, nobody outside can reach it.
read()
JSON.parse with ?? [] for a first visit, and try/catch for corrupt text. Falls back to an empty list instead of crashing the app.
commit(next)
The single place state changes: assign, save, notify. Keeping this in one function is what stops the three jobs from getting out of sync.
toggle
Builds a new array (filter or spread) instead of pushing. Immutable update, exactly as in the arrays entry.
subscribe(fn)
Registers a listener and returns a function that unregisters it. That returned "cleanup" function is the same shape as the one a React effect returns.
GotchaThe try/catch around setItem has an empty-looking catch on purpose, with a comment saying why. Private-browsing modes and full storage throw, and losing persistence must not break the app.

async function renderHome() {
  const input = h('input', {
    class: 'search',
    type: 'search',
    placeholder: 'Search recipes, e.g. pasta',
    'aria-label': 'Search recipes',
    value: state.query,
  })
  const results = h('div')
  app.replaceChildren(input, results)

  async function load() {
    const signal = nextSignal()
    results.replaceChildren(status('Loading recipes...'))
    try {
      const data = await listRecipes(state, signal)
      const pages = Math.max(1, Math.ceil(data.total / PAGE_SIZE))

      results.replaceChildren(
        data.recipes.length === 0
          ? status(`No recipes match "${state.query}".`)
          : h('ul', { class: 'grid' }, data.recipes.map(card)),
        h('div', { class: 'pager' },
          h('button', { class: 'btn', disabled: state.page <= 1, onclick: () => { state.page--; load() } }, 'Previous'),
          h('span', null, `Page ${state.page} of ${pages}`),
          h('button', { class: 'btn', disabled: state.page >= pages, onclick: () => { state.page++; load() } }, 'Next'),
        ),
      )
    } catch (err) {
      if (err.name === 'AbortError') return
      results.replaceChildren(status(err.message, 'error'))
    }
  }

  input.addEventListener('input', debounce(() => {
    state.query = input.value
    state.page = 1
    load()
  }, 400))

  load()
}

Walk through it

  1. Create the input once and the empty results container, then app.replaceChildren(input, results). Re-rendering results later never recreates the input, so it keeps focus and what you typed.
  2. load() gets a fresh signal, shows "Loading recipes...", awaits the API, then swaps the container's children for the cards and the pager.
  3. Pages: Math.ceil(total / PAGE_SIZE) with a minimum of 1, so an empty result still reads "Page 1 of 1".
  4. Empty state: zero recipes shows a friendly message that includes what was searched for.
  5. Pager buttons change state.page and call load() again. disabled is a real property, set from a boolean expression.
  6. catch: an AbortError means a newer request replaced this one, so return silently. Anything else is a real failure and its message is shown.
  7. Search input: the input listener is wrapped in debounce (400 ms). When it finally fires it saves the text, resets to page 1 (page 5 of a different search makes no sense), and loads.

// ---------- router ----------

const routes = [
  { pattern: /^#\/?$/, view: renderHome },
  { pattern: /^#\/recipe\/(\d+)$/, view: renderDetail },
  { pattern: /^#\/favorites$/, view: renderFavorites },
]

function route() {
  inflight?.abort()
  const hash = location.hash || '#/'
  const match = routes.map((r) => [r, hash.match(r.pattern)]).find(([, m]) => m)

  if (match) {
    const [{ view }, m] = match
    view(m.slice(1))
  } else {
    app.replaceChildren(h('p', { class: 'status' }, 'That page does not exist. ', h('a', { href: '#/' }, 'Go back home'), '.'))
  }
  updateNav()
}

function updateNav() {
  const hash = location.hash || '#/'
  document.getElementById('nav-saved').textContent = `Saved (${favorites.list().length})`
  document.getElementById('nav-browse').classList.toggle('active', !hash.startsWith('#/favorites'))
  document.getElementById('nav-saved').classList.toggle('active', hash.startsWith('#/favorites'))
}
  1. On every hashchange, route() aborts any request still running for the old page.
  2. It tries each pattern with String.prototype.match and keeps the first match with find.
  3. It calls the matching view with the captured values; otherwise it shows the "does not exist" message. That is the 404 page.
  4. updateNav() refreshes the counter and highlights the current link by toggling the active class.

What React is, a project from scratch, JSX, components and props, lists and keys, conditional rendering, state, events and forms, how rendering works, and how to think in React.

React is a JavaScript library for building user interfaces. It does one job: given the current data, work out what the screen should look like, and update the page to match. It is a library, not a full framework: routing, data fetching and styling come from other packages you choose.

How does React update fast? Reconciliation

Each render produces a tree of lightweight element objects (often called the virtual DOM). React compares the new tree with the previous one (diffing) and applies only the changes to the real DOM. Touching the real DOM is the slow part, so this keeps updates cheap. The comparison follows two rules: elements of a different type are thrown away and rebuilt, and in lists a key says which item is which.

To render a list, map the data to elements. Each element in the array needs a key: a stable, unique value that tells React which item is which between renders, so it can move, keep or remove the right DOM nodes.

Good keys

Database ids, slugs, any value that is unique and stays with the item. For static lists that never reorder, the index is acceptable.

Bad keys

Math.random() (new key every render, so everything is rebuilt) and the array index in a list that can reorder, filter or delete.

With index keys, React sees "the item at position 0 is still here, only its name changed", so it reuses the first row's DOM and the typed text stays there. The text now sits next to the wrong recipe. With id keys React knows the Pasta row was removed, and Soup keeps its own input. Gotchas
  • The key goes on the outermost element returned by map, not on something inside the child component.
  • Keys only need to be unique among siblings, not across the whole app.
  • key is not a prop: your component cannot read props.key. Pass the id as another prop if you need it.
  • Forgetting keys gives a console warning: "Each child in a list should have a unique key prop". Treat it as a bug report.
  • You can change a key on purpose to reset a component: <Form key={user.id} /> throws away the old form's state when the user changes.

What to remember

  • A component re-renders when: its own state changes, its parent re-renders (even with identical props, unless memoised), or a context it reads changes.
  • Re-render is not a DOM update. React compares output and only commits real differences. Many re-renders are cheap and fine.
  • Render must be pure: same props, state and context in, same JSX out. No mutating variables outside, no Math.random() or Date.now() in the output, no fetches.
  • StrictMode calls your component (and effects) an extra time in development to flush out impurity. A double log is normal.
  • State updates are batched: several setX calls in one handler give one re-render.
  • Position and type identify state. Same type at the same place in the tree keeps its state. A different type, or a different key, resets it.
Gotcha: React is not slow by defaultDo not wrap everything in memo "for performance". Measure first with the React DevTools Profiler. Typical wins come from keeping state close to where it is used, and from not doing heavy work during render.

Fetching in an effect, and the race condition

Requests can finish in a different order than they started. Without protection, a slow old response overwrites a newer one. The fix is the cleanup function: mark the old run as stale (or abort the request).

import { useEffect, useState } from "react";

// a fake API: answers for "p" are slow (60ms), everything else is fast
const search = (q) => new Promise((r) => setTimeout(() => r("results for " + q), q === "p" ? 60 : 5));

function Unprotected({ q }) {
  const [result, setResult] = useState("...");
  useEffect(() => { search(q).then(setResult); }, [q]);                  // no cleanup
  return <p>{result}</p>;
}

function Protected({ q }) {
  const [result, setResult] = useState("...");
  useEffect(() => {
    let ignore = false;
    search(q).then((r) => { if (!ignore) setResult(r); });
    return () => { ignore = true; };                                      // the old run becomes stale
  }, [q]);
  return <p>{result}</p>;
}

You might not need an effect

Effects are an escape hatch for talking to things outside React. Many effects are really mistakes:

You wrote an effect to...Do this instead
Compute fullName or a filtered list from stateCalculate it during render: const full = first + " " + last. (useMemo only if it is truly expensive)
Reset state when a prop changesGive the component a key based on that prop, or restructure so the state is not needed.
React to a user click (send a request, show a toast)Do it in the event handler. Effects are for things caused by rendering, handlers for things caused by the user.
Notify a parent after a state changeCall the parent's callback in the same event handler that sets the state.
Chain effects that set state to trigger each otherCompute everything in one place, or use a reducer.

Good uses: subscribing to the browser (resize, online), timers, integrating non-React widgets, syncing to localStorage or the document title, and fetching data when no data library is in use.

Gotchas
  • An effect function cannot be async (it would return a promise, not a cleanup). Define an async function inside it and call it.
  • Stale closure: an effect that uses count but has [] as dependencies keeps seeing the first value forever. The exhaustive-deps lint rule catches this. Obey it.
  • Objects and functions created inside the component are new on every render, so as dependencies they re-run the effect every time. Depend on primitives, or move the object out, or memoise it.
  • An effect that sets state it depends on, without a guard, loops forever.

When to use them

  • Default: do not. Re-rendering is usually cheap. Adding memoisation everywhere adds code and bugs (stale dependency arrays).
  • Use useMemo for a genuinely expensive calculation (filtering thousands of rows), after measuring.
  • Use memo + useCallback together for a heavy child that re-renders often with unchanged props.
  • Use useMemo/useCallback to keep a stable reference that is a dependency of an effect, or the value of a context (see the context entry).

useReducer is useState for state with several related fields or many kinds of change. You write one pure function, the reducer, that takes the current state and an action (a plain object describing what happened) and returns the next state. Components send actions with dispatch.

import { useReducer } from "react";

function cartReducer(state, action) {
  switch (action.type) {
    case "add": {
      const found = state.find((l) => l.id === action.id);
      return found
        ? state.map((l) => (l.id === action.id ? { ...l, qty: l.qty + 1 } : l))
        : [...state, { id: action.id, qty: 1 }];
    }
    case "remove":
      return state.filter((l) => l.id !== action.id);
    case "clear":
      return [];
    default:
      throw new Error("Unknown action: " + action.type);   // fail loudly on typos
  }
}

    <div>

      <button id="c" onClick={() => dispatch({ type: "clear" })}>clear</button>
      <p>{total} items: {lines.map((l) => `${l.id} x${l.qty}`).join(", ")}</p>
    </div>
  );
}

When to use context, and when not

  • Good fit: values that are read in many places and change rarely (auth user, theme, locale, a small shared store).
  • Context is not a global state manager. Every consumer of a context re-renders when its value changes, even if it only uses one field. For large, fast-changing shared state use several small contexts, or a library (Zustand, Redux Toolkit, Jotai).
  • Try composition first: pass children or finished elements down (<Layout sidebar={<Sidebar user={user} />} />) to avoid drilling without a context.
  • Wrap the context in a custom hook (useFavorites) so consumers never touch the raw context.
Gotchas
  • A component can only read context from a provider above it. Reading outside gives the default value.
  • Keep the provider near the top (in main.jsx), but as low as is practical for the data it serves.
  • Putting a provider and a hook in one file triggers a Fast Refresh lint warning (react/only-export-components). It is harmless; split the hook into its own file to silence it.

The two rules

  1. Call hooks only at the top level of a component or custom hook: not inside if, loops, nested functions, or after an early return. React identifies each hook by the order of the calls, so the order must be the same on every render.
  2. Call hooks only from React functions: components and other hooks (functions whose name starts with use), never from ordinary functions or event handlers.

The eslint-plugin-react-hooks rules enforce both and are already on in the Vite template.

A custom hook is simply a function whose name starts with use and that calls other hooks. It lets you reuse stateful logic (not state itself: each component that calls it gets its own copy of the state).

useDebounce, from the project

import { useEffect, useState } from 'react'

// returns `value`, but only after it has stopped changing for `delay` ms
export function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value)

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay)
    // cleanup runs before the next effect, so a new keystroke cancels the old timer
    return () => clearTimeout(id)
  }, [value, delay])

  return debounced
}
  1. value arrives on every keystroke. debounced state starts as the same value.
  2. Every time value or delay changes, the effect starts a timer that will copy value into state.
  3. If the value changes again before the timer fires, React runs the cleanup first, which cancels the old timer, then starts a new one. Only a value that stays still for delay ms gets through.
  4. The component re-renders when debounced changes, and everything depending on it (the API request) updates.

useAsync, from the project

import { useEffect, useState } from 'react'

// runs load(signal) whenever deps change and tracks loading, success and error.
// Stale requests are aborted, so a slow old response can never overwrite a newer one.
export function useAsync(load, deps) {
  const [state, setState] = useState({ status: 'loading', data: null, error: null })

  useEffect(() => {
    const controller = new AbortController()
    setState((prev) => ({ ...prev, status: 'loading', error: null }))

    load(controller.signal)
      .then((data) => setState({ status: 'success', data, error: null }))
      .catch((error) => {
        if (error.name === 'AbortError') return
        setState({ status: 'error', data: null, error })
      })

    return () => controller.abort()
    // load is a new function every render; the caller's deps decide when to re-run
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps)

  return state
}

Error boundaries

If a component throws while rendering, React unmounts the whole tree unless an error boundary above it catches the error and shows a fallback. A boundary must be a class component (the one place React still requires one), or use the react-error-boundary package.

import { Component } from 'react'

// error boundaries are still the one place React needs a class component
export default class ErrorBoundary extends Component {
  state = { error: null }

  static getDerivedStateFromError(error) {
    return { error }
  }

  componentDidCatch(error, info) {
    console.error('Caught by ErrorBoundary:', error, info.componentStack)
  }

  render() {
    if (this.state.error) {
      return (
        <div role="alert" className="status error">
          <p>Something broke on this page.</p>
          <button type="button" className="btn" onClick={() => this.setState({ error: null })}>
            Try again
          </button>
        </div>
      )
    }
    return this.props.children
  }
}
state = { error: null }
Class field: the initial state, no constructor needed.
static getDerivedStateFromError
Called during rendering after a descendant threw. Return the new state: this is how the boundary switches to the fallback.
componentDidCatch
Called after the error is caught. Log it or send it to an error tracker (Sentry).
render()
If there is an error, return the fallback; otherwise this.props.children.
Try again
Clears the error, so React tries rendering the children once more.

Accessibility checklist for React apps

  • Use the right element: button for actions, a or Link for navigation, ul/li for lists, main, nav, header landmarks. A div onClick is not keyboard accessible.
  • Every input has a visible label (htmlFor + id) or an aria-label. Images have meaningful alt, or alt="" when decorative.
  • Toggle buttons expose state with aria-pressed (as in FavoriteButton).
  • Loading and error messages use role="status" or role="alert" so screen readers announce them.
  • After a route change, move focus to the new page heading (SPAs do not do this for you), and update document.title.
  • Everything works with the keyboard alone: Tab order is logical, focus is visible (never outline: none without a replacement).
  • Colour contrast of text is at least 4.5:1, and meaning is never conveyed by colour alone.
  • Check with the Lighthouse tab, the eslint-plugin-jsx-a11y lint rules, and an axe browser extension. Then actually try a screen reader.

Client state

Belongs to the UI: is the menu open, what is typed in the box, which tab is selected. Use useState, useReducer, context. For bigger shared state: Zustand, Jotai, Redux Toolkit.

const BASE = 'https://dummyjson.com/recipes'

export const PAGE_SIZE = 12

async function getJson(url, signal) {
  const res = await fetch(url, { signal })
  // fetch only rejects on network failure, so a 404 or 500 has to be checked by hand
  if (!res.ok) throw new Error(`Request failed (${res.status})`)
  return res.json()
}

export function listRecipes({ query = '', page = 1 } = {}, signal) {
  const skip = (page - 1) * PAGE_SIZE
  const term = query.trim()
  const path = term ? `${BASE}/search?q=${encodeURIComponent(term)}&` : `${BASE}?`
  return getJson(`${path}limit=${PAGE_SIZE}&skip=${skip}`, signal)
}

export function getRecipe(id, signal) {
  return getJson(`${BASE}/${id}`, signal)
}

import { useEffect, useState } from 'react'

// runs load(signal) whenever deps change and tracks loading, success and error.
// Stale requests are aborted, so a slow old response can never overwrite a newer one.
export function useAsync(load, deps) {
  const [state, setState] = useState({ status: 'loading', data: null, error: null })

  useEffect(() => {
    const controller = new AbortController()
    setState((prev) => ({ ...prev, status: 'loading', error: null }))

    load(controller.signal)
      .then((data) => setState({ status: 'success', data, error: null }))
      .catch((error) => {
        if (error.name === 'AbortError') return
        setState({ status: 'error', data: null, error })
      })

    return () => controller.abort()
    // load is a new function every render; the caller's deps decide when to re-run
    // eslint-disable-next-line react-hooks/exhaustive-deps
  }, deps)

  return state
}
import { useEffect, useState } from 'react'

// returns `value`, but only after it has stopped changing for `delay` ms
export function useDebounce(value, delay = 400) {
  const [debounced, setDebounced] = useState(value)

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay)
    // cleanup runs before the next effect, so a new keystroke cancels the old timer
    return () => clearTimeout(id)
  }, [value, delay])

  return debounced
}
Lint notenpm run lint will print a warning on useAsync.js about exhaustive-deps. The linter can only check a dependency list it can read, and here the list is the variable deps passed in by the caller. The hook's whole purpose is that the caller decides when to reload, so the warning is expected. A bigger project would swap this hook for TanStack Query, which solves the same problem with a reviewed implementation.

The nav bar shows "Saved (3)", every card has a Save button, and the Favorites page lists them. These places are far apart in the tree, so the list lives in a provider at the top. Create src/context/favorites.jsx:

import { createContext, useContext, useEffect, useMemo, useReducer } from 'react'

const FavoritesContext = createContext(null)
const STORAGE_KEY = 'recipe-box:favorites'

function reducer(state, action) {
  switch (action.type) {
    case 'toggle': {
      const exists = state.some((r) => r.id === action.recipe.id)
      return exists
        ? state.filter((r) => r.id !== action.recipe.id)
        : [...state, action.recipe]
    }
    case 'clear':
      return []
    default:
      throw new Error(`Unknown action: ${action.type}`)
  }
}

// third argument of useReducer: runs once to build the initial state
function readStored() {
  try {
    return JSON.parse(localStorage.getItem(STORAGE_KEY)) ?? []
  } catch {
    return []
  }
}

export function FavoritesProvider({ children }) {
  const [favorites, dispatch] = useReducer(reducer, undefined, readStored)

  useEffect(() => {
    try {
      localStorage.setItem(STORAGE_KEY, JSON.stringify(favorites))
    } catch {
      // private mode or full storage: the app still works, it just forgets
    }
  }, [favorites])

  const value = useMemo(
    () => ({
      favorites,
      isFavorite: (id) => favorites.some((r) => r.id === id),
      toggle: (recipe) => dispatch({ type: 'toggle', recipe }),
      clear: () => dispatch({ type: 'clear' }),
    }),
    [favorites],
  )

  return <FavoritesContext value={value}>{children}</FavoritesContext>
}

export function useFavorites() {
  const ctx = useContext(FavoritesContext)
  if (!ctx) throw new Error('useFavorites must be used inside <FavoritesProvider>')
  return ctx
}
reducer
A pure function: given the old list and an action, return the new list. toggle removes the recipe if present, otherwise adds it, always building a new array (never push). The default case throws, so a typo in an action type is a loud error instead of a silent bug.
useReducer(reducer, undefined, readStored)
The third argument is an initializer: readStored runs once on the first render to load saved favourites. Passing the function (not calling it) avoids reading localStorage on every render. The JSON parse is in a try/catch because stored data can be missing or corrupt.
useEffect(... [favorites])
After each change, write the list back. Syncing with an outside system (localStorage) is exactly what an effect is for.
useMemo(... [favorites])
Builds the context value object only when the list changes. Without it a new object every render would re-render every consumer even when nothing changed.
<FavoritesContext value=...>
React 19 syntax. In React 18 write <FavoritesContext.Provider value=...>.
useFavorites()
A small custom hook that reads the context and throws a helpful message if a component is used outside the provider. Better than a confusing "cannot destructure of null" later.

Home: search, results, paging

import { useState } from 'react'
import { listRecipes, PAGE_SIZE } from '../api.js'
import RecipeCard from '../components/RecipeCard.jsx'
import { useAsync } from '../hooks/useAsync.js'
import { useDebounce } from '../hooks/useDebounce.js'

export default function Home() {
  const [text, setText] = useState('')
  const [page, setPage] = useState(1)
  const query = useDebounce(text, 400)

  const { status, data, error } = useAsync(
    (signal) => listRecipes({ query, page }, signal),

  )

  // reset the page in the handler that caused the change, not in an effect
  function handleSearch(e) {
    setText(e.target.value)
    setPage(1)
  }

  const pages = data ? Math.max(1, Math.ceil(data.total / PAGE_SIZE)) : 1

  return (
    <>
      <input
        className="search"
        type="search"
        placeholder="Search recipes, e.g. pasta"
        aria-label="Search recipes"
        value={text}
        onChange={handleSearch}
      />

      {status === 'error' && <p className="status error" role="alert">{error.message}</p>}
      {status === 'loading' && !data && <p className="status" role="status">Loading recipes...</p>}

      {data && (
        <>
          {data.recipes.length === 0 ? (
            <p className="status">No recipes match "{query}".</p>

          </div>

Reading Home in sections

lines 8-10
Two pieces of state the user controls: the text in the box and the page number. query is the debounced copy of text.
lines 12-15
useAsync with deps [query, page]. When either changes, the old request is aborted and a new one starts. Returns status, data and error.
handleSearch
Sets the text and resets to page 1 in the same handler. A beginner's version resets the page in an effect, which causes an extra render and a flicker. When one user action causes two state changes, do both in the handler.
pages
Derived from data.total in the render. Never stored.
the three-way UI
status === 'error' shows the message. 'loading' && !data shows "Loading" only when there is nothing to show yet; when moving to the next page the old cards stay visible (the hook keeps the previous data) until the new ones arrive. Then either an empty-state message or the grid.
setPage((p) => p - 1)
The functional update form, because the new page depends on the previous one.
key={recipe.id}
A stable id from the data, never the array index, so React matches the right card to the right item when the list changes.

Unit 12: Testing React Apps

Vitest and React Testing Library: setup, queries, user events, async UI, mocking fetch, testing hooks and context, reading failures, and what is worth testing.

A test is a small program that uses your code the way a user (or another part of the code) would, and fails loudly when the result is wrong. Tests let you change code without fear: refactor, upgrade a library, add a feature, then run one command and know what broke.

The guiding rule of React Testing Library: the more your tests resemble the way your software is used, the more confidence they give. So you test what appears on screen and what happens when a user clicks and types, not internals like state variables or which hook was called.

KindTestsToolsSpeed
UnitA pure function or a hook alone (api.js, the reducer, useDebounce)Vitest, node:testMilliseconds
Component / integrationA component or page with its children, in a simulated browser (jsdom)Vitest + Testing LibraryTens of ms
End to end (e2e)The real app in a real browser, real clicksPlaywright, CypressSeconds

Most of your tests should be the first two kinds: cheap and reliable. Keep a handful of e2e tests for the critical journeys (search, open, save, reload).

The cast

Vitest
The test runner made for Vite. It finds *.test.js(x) files, runs them, reports results. Same config file and plugins as the app, and a Jest-compatible API (test, expect, vi.fn).
jsdom
A simulated browser (DOM, events, localStorage) written in JavaScript so tests run in Node with no real browser window.
@testing-library/react
render, screen, renderHook, cleanup. Mounts components and finds things the way users do.
@testing-library/user-event
Simulates real interactions: a click is pointer events, focus and click together; typing is a key press per character.
@testing-library/jest-dom
Readable assertions: toBeInTheDocument(), toHaveTextContent(), toBeDisabled(), toHaveAttribute().

What to test (and what to skip)

Worth testing
  • Each state a user can see: loading, data, empty, error.
  • Interactions: click Save, the label changes and the count goes up.
  • Logic that is easy to get wrong: reducers, URL building, debounce, formatting.
  • Things that once broke (write the test first, then fix the bug).
  • Persistence: saved favourites come back on the next mount.
Usually not worth it
  • Whether useState was called, or what a state variable is named.
  • Exact CSS or pixel layout (use visual or e2e checks).
  • Third-party libraries (they have their own tests).
  • Every possible prop combination of a trivial component.
  • Snapshot tests of big trees: they fail for no reason and everyone just updates them.
Vitest or node:test?Unit 8's plain-JavaScript app used the built-in node --test because it had no build step and no DOM. Vitest is the natural choice in a Vite project: it understands JSX, imports and the Vite config without extra setup, and runs a jsdom environment.

The three query families

FamilyNo matchUse it for
getBy... / getAllBy...Throws an error (with a helpful dump)Things that must be there now.
queryBy... / queryAllBy...Returns nullAsserting something is absent: expect(screen.queryByText('Loading')).not.toBeInTheDocument()

Which query to choose (in priority order)

  1. getByRole: the best. Matches how assistive technology sees the page. getByRole('button', { name: /save/i }), getByRole('heading', { level: 2 }), getByRole('link', { name: 'Back' }).
  2. getByLabelText: form fields found by their label (aria-label also works), as in getByLabelText('Search recipes').
  3. getByPlaceholderText, getByText: visible text content.
  4. getByAltText, getByTitle: images and titles.
  5. getByTestId: last resort, an invented data-testid attribute that real users never see. Use only when nothing semantic fits (the context test uses it for a count display of a throwaway probe).

The nice side effect: if getByRole cannot find your button, your page probably has an accessibility problem too.

Common mistakes
  • Not awaiting a user.* call or a findBy*: the test runs ahead of React and fails (or worse, passes by accident).
  • Using getBy for something that appears after a fetch. Use findBy.
  • Asserting absence with getBy (it throws, so the test fails for the wrong reason). Use queryBy.
  • Wrapping calls in act yourself. Testing Library already does it; hand-written act is almost never needed.
  • Copying the implementation into the test (expect(setPage).toHaveBeenCalled). Test the result on screen instead.

Testing a hook alone with renderHook and fake time

import { act, renderHook } from '@testing-library/react'
import { afterEach, beforeEach, expect, test, vi } from 'vitest'
import { useDebounce } from './useDebounce.js'

beforeEach(() => vi.useFakeTimers())
afterEach(() => vi.useRealTimers())

test('only updates after the delay has passed', () => {
  const { result, rerender } = renderHook(({ value }) => useDebounce(value, 300), {
    initialProps: { value: 'a' },
  })

  rerender({ value: 'ab' })
  expect(result.current).toBe('a')

  act(() => vi.advanceTimersByTime(299))
  expect(result.current).toBe('a')

  act(() => vi.advanceTimersByTime(1))
  expect(result.current).toBe('ab')
})

test('restarts the timer when the value changes again', () => {
  const { result, rerender } = renderHook(({ value }) => useDebounce(value, 300), {
    initialProps: { value: 'a' },
  })

  rerender({ value: 'ab' })
  act(() => vi.advanceTimersByTime(200))
  rerender({ value: 'abc' })
  act(() => vi.advanceTimersByTime(200))
  expect(result.current).toBe('a')

  act(() => vi.advanceTimersByTime(100))
  expect(result.current).toBe('abc')
})
  • renderHook(fn, { initialProps }) mounts a tiny invisible component that calls your hook. result.current is the latest return value; rerender(newProps) simulates the parent passing a new value.
  • vi.useFakeTimers() replaces setTimeout with a clock the test controls. vi.advanceTimersByTime(299) jumps 299 ms instantly. The first test checks the edge: at 299 ms the value is still old, at 300 ms it updates. No real waiting.
  • act(() => ...) around the time jump is the one place you do need it: you are changing React state from outside React's event system.
  • The second test proves the "restart" behaviour: a new value at 200 ms cancels the old timer, so 400 ms total is not enough yet.
  • The test file ends with .js because it contains no JSX.

Testing context, persistence and an expected error

import { render, screen } from '@testing-library/react'
import userEvent from '@testing-library/user-event'
import { expect, test, vi } from 'vitest'
import { pasta, soup } from '../test/fixtures.js'
import { FavoritesProvider, useFavorites } from './favorites.jsx'

function Probe() {
  const { favorites, toggle, clear } = useFavorites()
  return (
    <>
      <p data-testid="count">{favorites.length}</p>
      <button onClick={() => toggle(pasta)}>toggle pasta</button>
      <button onClick={() => toggle(soup)}>toggle soup</button>
      <button onClick={clear}>clear</button>
    </>
  )
}

const setup = () =>
  render(
    <FavoritesProvider>
      <Probe />
    </FavoritesProvider>,
  )

test('toggle adds and removes a recipe', async () => {
  const user = userEvent.setup()
  setup()

  await user.click(screen.getByText('toggle pasta'))
  expect(screen.getByTestId('count')).toHaveTextContent('1')

  await user.click(screen.getByText('toggle pasta'))
  expect(screen.getByTestId('count')).toHaveTextContent('0')
})

test('saves to localStorage and restores on the next mount', async () => {
  const user = userEvent.setup()
  const first = setup()
  await user.click(screen.getByText('toggle pasta'))
  await user.click(screen.getByText('toggle soup'))
  first.unmount()

  setup()
  expect(screen.getByTestId('count')).toHaveTextContent('2')
})

test('clear empties the list', async () => {
  const user = userEvent.setup()
  setup()
  await user.click(screen.getByText('toggle pasta'))
  await user.click(screen.getByText('clear'))
  expect(screen.getByTestId('count')).toHaveTextContent('0')
})

test('the hook throws outside the provider', () => {
  const quiet = vi.spyOn(console, 'error').mockImplementation(() => {})
  expect(() => render(<Probe />)).toThrow(/FavoritesProvider/)
  quiet.mockRestore()
})
  • A probe component: the provider has no UI, so the test defines a tiny component that uses useFavorites() and shows the result. It is the simplest way to test a context.
  • Persistence: render, save two recipes, unmount(), render again. The count is 2 because the new provider read localStorage. That is the whole "survives a refresh" feature in six lines.
  • An expected error: rendering without the provider must throw our helpful message. React also logs the error to the console, which would clutter the test output, so vi.spyOn(console, 'error').mockImplementation(() => {}) silences it, and mockRestore() brings it back.
  • The reducer here is covered through behaviour. If it grew complex, you could also export it and test it directly as a plain function.

JSX and components

  • A component is a function with a Capitalised name that returns JSX. Lowercase means an HTML tag.
  • Return one root: wrap in <>...</> (fragment) when you do not want an extra div.
  • Attributes are camelCase: className, htmlFor, onClick, tabIndex. Every tag must be closed (<img />).
  • { } embeds any expression (not statements like if). Use &&, ? : or early returns for conditions.
  • {count && <X />} prints 0 when count is 0. Write count > 0 &&.
  • Lists: items.map((x) => <Row key={x.id} {...x} />) with a stable, unique key.
  • style takes an object with camelCase keys. {style={{ width: 10 }}} is an object inside the braces.
  • Props flow down and are read-only. State is owned by one component; to share it, lift it to the nearest common parent.

IMPWrite debounce(fn, ms): calling it many times quickly runs fn once, with the last arguments, after ms of quiet.

One timer variable lives in the closure. Each call cancels the previous timer and starts a new one.

function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}

async function pool(tasks, limit) {
  const results = [];
  let next = 0;
  async function worker(id) {
    while (next < tasks.length) {
      const i = next++;                       // claim the next task (safe: no await between read and ++)
      results[i] = await tasks[i](id);        // store by index so order is preserved
    }
  }
  await Promise.all(Array.from({ length: limit }, (_, k) => worker(k + 1)));
  return results;
}

IMPWhat is the difference between var, let and const?

var is function-scoped, hoisted with the value undefined, and can be redeclared. let and const are block-scoped and hoisted but unusable until their declaration line (the temporal dead zone, which throws a ReferenceError). const forbids reassigning the binding but the object it points to can still change. Default to const.

IMPWhat is a closure and why is it useful?

A function together with the variables of the scope where it was created. It keeps access to them even after that outer function has returned. Uses: private state (makeCounter), factories (debounce, once), callbacks that remember context, and React hooks themselves. Pitfall: a closure keeps the old value of anything it captured, which causes stale-value bugs in timers and effects.

IMPExplain the event loop. Microtasks versus macrotasks?

JavaScript runs one thing at a time on a call stack. When the stack is empty the loop first runs all queued microtasks (promise then, await continuations, queueMicrotask), then takes one macrotask (timer, click, network callback), then drains microtasks again, and renders when it can. That is why setTimeout(f, 0) still runs after a resolved promise's callback, and why a long synchronous loop freezes the page.

IMP== versus ===?

=== compares value and type with no conversion. == converts types first using complicated rules ("5" == 5, [] == false are true). Use === always. The one accepted use of == is x == null, which matches both null and undefined.

IMPHow is this determined?

By how the function is called, not where it is written: obj.method() sets it to obj; a plain call gives undefined in strict mode/modules; new makes it the new object; call/apply/bind set it explicitly. Arrow functions have no own this: they use the one from the surrounding code, which is why they suit callbacks inside methods. A method passed as a callback loses its this (fix with an arrow or bind).

IMPPromises versus async/await. How do you handle errors?

async/await is syntax over promises: an async function always returns a promise, and await pauses it until the promise settles. Handle errors with try/catch around await, or .catch() on a chain. A rejected promise nobody handles raises "Uncaught (in promise)". Run independent work in parallel with Promise.all; use allSettled when you want every result even if some fail.

Does fetch reject on a 404?

No. It rejects only on network failure (offline, DNS, CORS block). For any HTTP response, even 404 or 500, the promise resolves. Check res.ok or res.status and throw yourself.

What is hoisting?

Declarations are registered at the start of their scope before code runs. Function declarations are fully usable earlier. var exists as undefined. let/const/class exist but are in the temporal dead zone until declared. Function expressions and arrows assigned to a variable follow the variable's rules.

Explain prototypes. What does class add?

Every object has an internal link to another object, its prototype. A property lookup walks up that chain until found or null. Methods shared by all instances live on the prototype instead of being copied. class is cleaner syntax over the same mechanism, adding constructor, extends/super, static, getters/setters and truly private #fields.

IMPShallow copy versus deep copy?

A shallow copy ({...o}, [...a], Object.assign) copies the top level; nested objects are still shared, so changing copy.address.city changes the original too. A deep copy duplicates everything: structuredClone(value) (not for functions or class instances' methods). In React state updates, copy only the path you change.

map, filter, reduce, forEach: when to use which?

map returns a new array of the same length (transform). filter returns a subset. reduce folds to one value (sum, object, grouped data). forEach returns nothing and is for side effects only. find/some/every answer questions about the contents. Prefer these over index loops when readability improves, but a for...of is better when you need await in order or an early break.

Debounce versus throttle?

Debounce runs after calls have stopped for a delay (search-as-you-type, auto-save). Throttle runs at most once per interval while calls keep coming (scroll, resize, mousemove handlers).

IMPWhat is event delegation? Bubbling versus capturing?

Events travel from the window down to the target (capturing) and back up (bubbling). Delegation puts one listener on a parent and uses event.target.closest(selector) to find which child was hit, so it works for many items and for items added later. preventDefault() stops the browser's default action (following a link, submitting a form). stopPropagation() stops the event travelling further. They are different.

CommonJS versus ES modules?

CommonJS (require, module.exports) loads synchronously and is the older Node format. ES modules (import/export) are the standard: static (analysable, so bundlers can drop unused code), asynchronous, with top-level await, work in browsers and Node ("type": "module" or .mjs). Use ES modules for new code.

null versus undefined?

undefined means "no value assigned" (a missing property, an omitted argument, a function with no return). null is a deliberate "empty". null == undefined is true, null === undefined is false. typeof null is "object", a historical bug.

localStorage, sessionStorage, cookies?

localStorage: strings, about 5 MB, survives browser restarts, per origin, readable by any script on the page. sessionStorage: same API, cleared when the tab closes. Cookies: small, sent to the server with every request, can be HttpOnly (hidden from scripts) and Secure: the right place for session tokens. Never store secrets in localStorage.

IMPWhat is CORS?

A browser security rule: a page from origin A may only read responses from origin B if B's server allows it with Access-Control-Allow-Origin headers. It protects users, and the server (not the client code) must grant permission. "Preflight" OPTIONS requests check complex requests first. Fixes: use an API that sends the headers, configure your own server, or proxy through your backend.

IMPinnerHTML versus textContent, and what is XSS?

textContent inserts text, so any HTML in it is shown literally and is harmless. innerHTML parses HTML, so inserting user-provided text through it lets an attacker run script (cross-site scripting). Build elements with the DOM API or textContent, sanitize if HTML is unavoidable. React escapes values in JSX for the same reason; dangerouslySetInnerHTML is the escape hatch.

What is a pure function and why do we like them?

Same input, same output, no side effects (no mutating arguments, no network, no randomness or time). They are easy to test, cache and reason about, and React components and reducers are expected to be pure.

What causes memory leaks in JavaScript apps?

Listeners never removed, intervals never cleared, closures holding big objects, growing global caches, detached DOM nodes still referenced. In React: effects without cleanup (subscriptions, timers). Find them with the DevTools Memory tab by comparing heap snapshots.

Map versus plain object? Set?

A Map allows any key type, keeps insertion order, has size, and is built for frequent add/remove. A plain object is best for fixed records and JSON. A Set stores unique values; [...new Set(arr)] removes duplicates.

What are generators and iterators?

An iterator is an object with next() returning { value, done }; anything with [Symbol.iterator] works in for...of and spread. A generator function (function*) with yield builds iterators lazily, pausing at each yield, which allows infinite sequences and custom iteration.

What does ?? do and how is it different from ||?

a ?? b uses b only when a is null or undefined. a || b uses b for any falsy a, so a valid 0, "" or false would be replaced by mistake.

Why does 0.1 + 0.2 not equal 0.3?

Numbers are binary floating point; 0.1 and 0.2 cannot be represented exactly, so the sum is 0.30000000000000004. Use integers for money (cents), round for display with toFixed or Intl.NumberFormat, and compare with a small tolerance.

What is currying and function composition?

Currying turns f(a, b) into f(a)(b), which makes specialised functions easy (const add5 = add(5)). Composition builds a new function by chaining others: pipe(trim, lower, slug). Both rely on functions being values and on closures.

IMPWhat is React and what does "declarative" mean?

A library for building user interfaces from components. Declarative means you describe what the UI should look like for the current state and React works out the DOM changes. You write {items.map(...)}, not "create an li, append it, remove that one". On each render React compares the new element tree with the previous one and updates only what changed in the real DOM.

IMPState versus props?

Props are inputs passed from a parent: read-only inside the component. State is memory owned by a component that can change over time and triggers a re-render when set. Data flows one way, down: a parent passes values and callbacks as props; a child asks the parent to change state by calling a callback.

IMPWhen does a component re-render?

When its own state changes, when its parent re-renders (even if the props are identical, unless wrapped in memo), or when a context it reads changes. Re-rendering means calling the function again to get new JSX. It is cheap; only changed DOM nodes are touched. Do not optimise until measuring a problem.

IMPWhy are keys needed in lists? Why not use the index?

Keys let React match each item between renders, to keep the right state and DOM node with the right data when items are added, removed or reordered. With index keys, deleting the first item makes every later item "become" its neighbour, so input text, focus and animation state end up on the wrong rows. Use a stable id from the data. The index is fine only for static lists that never reorder.

IMPWhy must you not mutate state?

React detects changes by comparing references (Object.is). If you push into the same array and set it back, the reference is identical, so React may skip the update, and memoised children and effects do not notice. Always create a new object or array: spread, map, filter.

IMPIs setState synchronous? What are functional updates?

No. It schedules a re-render, and updates in the same event are batched. The variable you already read still holds the old value for the rest of that render. When the new value depends on the previous one, pass a function: setCount(c => c + 1). Calling setCount(count + 1) three times adds one; the functional form adds three.

IMPExplain useEffect: when does it run, what are dependencies and cleanup?

It runs after the component has rendered and the browser has painted, to synchronise with something outside React. The dependency array lists every reactive value used inside; the effect re-runs when one changes ([] means once after mount, none means after every render). The returned cleanup runs before the next run and on unmount: clear timers, unsubscribe, abort requests. In development StrictMode runs effects an extra time to expose missing cleanup.

IMPWhen should you NOT use an effect?

For values you can calculate during render (derived state), for reacting to a user event (do it in the handler), and for resetting state when a prop changes (use a key). Effects are for syncing with external systems: fetching, subscriptions, timers, the DOM, storage.

Controlled versus uncontrolled inputs?

Controlled: React state holds the value (value + onChange), so the UI always reflects state and you can validate or transform on every keystroke. Uncontrolled: the DOM holds the value; you read it on submit through a ref or FormData. Uncontrolled is simpler for simple forms; controlled when you need live feedback.

IMPWhat are the rules of hooks and why do they exist?

Call hooks only at the top level of a component or custom hook, never in conditions, loops or after an early return; and only from React functions. React stores hook state in a list by call order; if the order changes between renders it would hand state to the wrong hook ("Rendered more hooks than during the previous render").

useRef versus useState?

Both persist across renders. Changing state re-renders; changing ref.current does not. Use refs for DOM nodes (focus, scroll), timer ids, the previous value, and anything the UI does not display. If the screen must change, it is state.

useMemo, useCallback, React.memo: what and when?

useMemo caches a calculated value between renders; useCallback(fn, deps) is the same for a function; memo(Component) skips re-rendering a child whose props are unchanged. They only pay off when the calculation is really slow or a memoised child receives the value as a prop or dependency. Measure with the Profiler first; the React Compiler can add much of this automatically.

useState or useReducer?

useState for independent simple values. useReducer when several fields change together, the next state depends on an action, or you want the update rules in one testable pure function (the favourites list in Recipe Box).

IMPWhat is context and what is its drawback?

A way to make a value available to a whole subtree without passing props through every level (theme, current user, favourites). Every component that reads the context re-renders when its value changes, so keep contexts small and stable (memoise the value object), and do not use one big context for fast-changing state. For heavy shared state use a store library such as Zustand or Redux Toolkit.

What is "lifting state up"?

When two components need the same changing data, move the state to their closest common parent and pass it down as props along with setter callbacks. It keeps one source of truth and avoids copies that drift apart.

IMPHow do you fetch data correctly in a component?

Start the request in an effect (or use a data library), keep status/data/error in state, show loading and error UI, and cancel or ignore stale responses with an AbortController in the cleanup, otherwise a slow old response can overwrite a newer one (a race condition). For anything non-trivial prefer TanStack Query or SWR (caching, retries, deduplication) or a framework's data loading.

What is an error boundary?

A class component with getDerivedStateFromError (and optionally componentDidCatch) that catches errors thrown while rendering its children and shows a fallback instead of unmounting the whole app. It does not catch errors in event handlers, async code or itself.

How do you reduce bundle size and speed up the first load?

Route-level code splitting with React.lazy + Suspense, dropping heavy dependencies, compressing and lazy-loading images, checking what npm run build prints, serving with a CDN and caching hashed files forever.

CSR, SSR, SSG, and hydration?

Client-side rendering sends an empty HTML shell and React builds the page in the browser (a Vite app). Server-side rendering builds the HTML on the server for each request (fast first paint, good SEO). Static generation builds pages ahead of time. Hydration attaches React's event handling to server-made HTML in the browser. Frameworks like Next.js manage these choices.

What is new in React 19?

Actions (<form action={fn}>), useActionState, useFormStatus, useOptimistic, the use API for promises and context, ref as a regular prop (no forwardRef), context used directly as a provider, document metadata tags, and improved error reporting. Server Components and Server Actions arrive through frameworks.

Function components versus class components?

Function components with hooks are the standard. Classes still work and are required only for error boundaries. Rough mapping: this.state is useState, componentDidMount/Update/WillUnmount together are useEffect with cleanup.

What are fragments and portals?

A fragment (<></>) groups children without an extra DOM element. A portal (createPortal(children, domNode)) renders children into a different place in the DOM, such as a modal in document.body, while keeping them in the same React tree for state and context.

IMPHow does client-side routing work?

The router listens to the History API. A Link click calls history.pushState to change the address and tells React Router to render the matching route, with no page reload; back and forward fire popstate. The server must return index.html for unknown paths so a refresh on a deep URL still loads the app.

IMPHow do you test a React component?

With Vitest (or Jest) and Testing Library: render it inside the providers it needs, find elements the way a user would (getByRole, label, text), interact with user-event, await asynchronous UI with findBy, mock fetch, and assert on what is visible. Test behaviour, not implementation details like state variables. Add a few end-to-end tests with Playwright for key journeys.

How do you make a React app accessible?

Semantic elements (button, nav, main), labels on every input, alt text, keyboard operability and visible focus, aria-* attributes only where HTML falls short, announced status messages (role="status"/"alert"), focus management after navigation, sufficient colour contrast. Lint with jsx-a11y, test with Lighthouse and a screen reader.
