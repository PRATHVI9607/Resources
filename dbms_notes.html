DBMS Fundamentals

What is a DBMS?

A Database Management System is software that manages a collection of interrelated data. It provides an interface between the data and users/applications, ensuring data is stored, retrieved, and managed efficiently.

📦 Data
Raw facts stored in tables, files, or documents
🧩 DBMS Software
MySQL, PostgreSQL, Oracle, SQLite, SQL Server
👤 Users
DBA, Application Users, End Users, Programmers
🔧 Application
The frontend/backend that queries the DB via API or SQL

File System vs DBMS

File SystemDBMS
Data redundancy & inconsistencyControlled redundancy
No data sharingConcurrent data sharing
No backup/recoveryBuilt-in recovery mechanisms
No securityAccess control & permissions
No integrity constraintsEnforces constraints automatically
No query languageSQL for powerful queries

Data Independence

Logical Data Independence
Change conceptual schema without changing external schema (user views). Hardest to achieve.
Physical Data Independence
Change internal schema (storage) without changing conceptual schema. Easier to achieve.

💡
Key Terms: Schema = structure/definition of the database. Instance = actual data at a point in time. Metadata = data about data (stored in data dictionary / system catalog).

ER Model (Entity-Relationship)

ER model is a conceptual data model used to design databases at a high level before actual implementation.

Core Components

ComponentSymbolDescription
EntityRectangle □A real-world object (Student, Employee, Product)
Weak EntityDouble Rectangle ⧄Depends on another entity for existence (Order Item depends on Order)
AttributeEllipse ○Property of an entity (Name, Age, ID)
Key AttributeUnderlined EllipseUniquely identifies entity (StudentID)
Multivalued AttrDouble EllipseCan have multiple values (PhoneNumbers)
Derived AttrDashed EllipseComputed from other attrs (Age from DOB)
Composite AttrEllipse with sub-ellipsesMade of smaller parts (Name = First + Last)
RelationshipDiamond ◇Association between entities (Enrolled-In)
Identifying RelDouble DiamondRelationship that identifies a weak entity

Cardinality Ratios

1:1 One-to-One
One entity A relates to one entity B.
Person ↔ Passport
1:N One-to-Many
One A relates to many B.
Department → Employees
M:N Many-to-Many
Many A relate to many B.
Students ↔ Courses
N:1 Many-to-One
Many A relate to one B.
Employees → Manager

Participation Constraints

Total Participation (double line)
Every entity MUST participate. Every employee MUST work in a department.
Partial Participation (single line)
Entity MAY participate. Not every employee manages a department.

ER → Relational Mapping Rules

ER ConceptRelational Mapping
Strong Entity→ Table with all attributes; key becomes PK
Weak Entity→ Table; PK = partial key + PK of owner entity (FK)
1:1 Relationship→ Add FK to either side (prefer total participation side)
1:N Relationship→ Add FK on the N side (child) referencing the 1 side
M:N Relationship→ Create junction/bridge table with FKs from both entities
Multivalued Attr→ Create new table with PK of entity + the attribute
Composite Attr→ Include only the leaf/simple components as columns
Derived Attr→ Usually NOT stored; computed at query time

Generalization, Specialization & Aggregation

Generalization
Bottom-up. Combine Car and Truck → Vehicle. Extract common attributes.
Specialization
Top-down. Person → Employee, Student. Subsets with extra attributes.
Aggregation
Treat a relationship as an entity to allow relationships with other entities. Used when a relationship needs its own relationship.
✅
Quick Rule: If you need to track data about a relationship (like a salary for a Works-In relationship), it becomes an attribute of that relationship. If a relationship needs to participate in another relationship, use aggregation.

Relational Model & Keys

Key Terminology

TermDefinition
RelationA table with rows and columns
TupleA row in a table
AttributeA column in a table

CardinalityNumber of tuples (rows)

Types of Keys

SK
Super Key
Any set of attributes that can uniquely identify a tuple. May have extra (redundant) attributes. Example: {StudentID}, {StudentID, Name}, {StudentID, Age}
CK
Candidate Key
A minimal super key — no proper subset can uniquely identify. A table can have multiple CKs. Example: {StudentID} or {Email}
PK
Primary Key
The chosen candidate key. Cannot be NULL, must be unique. Only one PK per table.
AK
Alternate Key
Candidate keys NOT chosen as primary key. Also called secondary keys.
FK
Foreign Key
An attribute in table B that references the PK of table A. Enforces referential integrity. Can be NULL unless constrained. Orders.CustomerID → Customers.CustomerID
CPK
Composite Key
A key made of two or more attributes together. Common in junction tables. Example: (StudentID, CourseID) in Enrollment

Integrity Constraints

ConstraintRule
Domain ConstraintValues must be from the attribute's domain (e.g., Age must be integer)
Entity IntegrityPrimary key cannot be NULL
Referential IntegrityFK value must exist in referenced table's PK (or be NULL)
Key ConstraintPK must be unique in the relation
Semantic IntegrityBusiness rules (e.g., salary > 0, age between 18-65)

CREATE TABLE

CREATE TABLE students (
    student_id  INT          PRIMARY KEY AUTO_INCREMENT,
    name        VARCHAR(100) NOT NULL,
    email       VARCHAR(150) UNIQUE NOT NULL,
    age         INT          CHECK (age >= 18 AND age <= 100),

SELECT — Full Syntax

SELECT [DISTINCT] column1, column2, AGG(col) AS alias
FROM   table1
       [JOIN table2 ON table1.id = table2.fk]
WHERE  condition           -- filters BEFORE grouping
GROUP BY column1
HAVING   agg_condition   -- filters AFTER grouping
ORDER BY column1 [ASC|DESC]
LIMIT  10 OFFSET 20;      -- skip 20, take 10
⚠️
SQL Execution Order (NOT writing order):
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

WHERE Operators & Conditions

SELECT * FROM students
WHERE  age BETWEEN 18 AND 25          -- inclusive both ends
  AND  name LIKE 'A%'                  -- starts with A
  AND  name LIKE '_lice'               -- _ = exactly 1 char
  AND  dept_id IN (1, 2, 3)           -- value in list
  AND  dept_id NOT IN (4, 5)         -- not in list
  AND  phone IS NULL                   -- check for null
  AND  gpa IS NOT NULL               -- check not null
  OR   age > 30;

-- Comparison: =  !=  <>  >  <  >=  <=
-- Logical:    AND  OR  NOT

UPDATE

-- Update specific rows
UPDATE students
SET    gpa = gpa + 0.1,
       name = UPPER(name)
WHERE  dept_id = 1;

-- Update with subquery
UPDATE students
SET    dept_id = (
           SELECT dept_id FROM departments
           WHERE dept_name = 'Computer Science'
       )
WHERE  student_id = 5;

DELETE

-- Delete specific rows
DELETE FROM students
WHERE  gpa < 2.0;

-- Delete all rows (keeps table)
DELETE FROM students;

-- Delete with JOIN (MySQL)
DELETE s
FROM   students s
JOIN   departments d ON s.dept_id = d.dept_id
WHERE  d.dept_name = 'Closed';

UNION, INTERSECT, EXCEPT

-- UNION: combines results, removes duplicates
SELECT name FROM students
UNION
SELECT name FROM staff;

-- UNION ALL: keeps duplicates (faster)
SELECT name FROM students
UNION ALL
SELECT name FROM staff;

-- INTERSECT: rows in BOTH (PostgreSQL, not MySQL)
SELECT name FROM students
INTERSECT
SELECT name FROM staff;

-- EXCEPT/MINUS: rows in first but NOT second
SELECT name FROM students

SELECT name FROM staff;
✅

JOINs — Every Type Explained
◐
INNER JOIN
Only rows with matching values in BOTH tables
◓
LEFT JOIN
ALL rows from left + matched from right (NULLs for no match)
◒
RIGHT JOIN
ALL rows from right + matched from left
○
FULL OUTER JOIN
ALL rows from both (NULLs where no match)
⊠
CROSS JOIN
Cartesian product — every row × every row
⟲
SELF JOIN
A table joined with itself (hierarchies, comparisons)

JOIN Syntax Examples

-- INNER JOIN
SELECT s.name, d.dept_name
FROM   students s
INNER JOIN departments d ON s.dept_id = d.dept_id;

-- LEFT JOIN (students without a department shown as NULL)
SELECT s.name, d.dept_name
FROM   students s
LEFT JOIN departments d ON s.dept_id = d.dept_id;

-- Find students WITH NO department (anti-join pattern)
SELECT s.name
FROM   students s
LEFT JOIN departments d ON s.dept_id = d.dept_id
WHERE  d.dept_id IS NULL;

-- FULL OUTER JOIN (MySQL doesn't have this natively)
SELECT s.name, d.dept_name
FROM   students s
LEFT JOIN departments d ON s.dept_id = d.dept_id
UNION
SELECT s.name, d.dept_name
FROM   students s
RIGHT JOIN departments d ON s.dept_id = d.dept_id;

-- CROSS JOIN (generates all combinations)
SELECT s.name, c.course_name
FROM   students s
CROSS JOIN courses c;

-- SELF JOIN (find employee's manager)
SELECT e.name AS employee, m.name AS manager
FROM   employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;

-- Multiple JOINs
SELECT s.name, c.course_name, e.grade
FROM   students s
JOIN   enrollment e  ON s.student_id = e.student_id
JOIN   courses    c  ON e.course_id  = c.course_id
WHERE  e.grade >= 'B';
💡
NATURAL JOIN joins on all columns with the same name automatically. Avoid in production — fragile to schema changes. USING(col) is a safer shorthand: JOIN dept USING(dept_id)

GROUP BY & HAVING

-- Basic GROUP BY
SELECT   dept_id, COUNT(*) AS total, AVG(gpa) AS avg_gpa
FROM     students
GROUP BY dept_id;

-- HAVING: filter after grouping (WHERE can't use aggregates)
SELECT   dept_id, COUNT(*) AS total
FROM     students
GROUP BY dept_id
HAVING   COUNT(*) > 5;

-- WHERE + GROUP BY + HAVING together
SELECT   dept_id,
         MAX(gpa) AS top_gpa,
         MIN(gpa) AS low_gpa,
         COUNT(*) AS students
FROM     students
WHERE    gpa IS NOT NULL        -- filter before grouping
GROUP BY dept_id
HAVING   MAX(gpa) >= 3.5      -- filter after grouping
ORDER BY top_gpa DESC;

-- GROUP_CONCAT: list values in a group
SELECT   dept_id,
         GROUP_CONCAT(name ORDER BY name SEPARATOR ', ') AS student_names
FROM     students
GROUP BY dept_id;
⚠️
GROUP BY Rule: Every column in SELECT must either be in GROUP BY or wrapped in an aggregate function. (MySQL has a lenient mode; PostgreSQL enforces strictly.)

ROLLUP & CUBE

-- ROLLUP: subtotals + grand total
SELECT   dept_id, year, SUM(salary)
FROM     employees
GROUP BY dept_id, year WITH ROLLUP;
-- generates: (dept,year), (dept,NULL), (NULL,NULL)

-- CUBE: all possible subtotals (PostgreSQL)
GROUP BY CUBE(dept_id, year)
-- generates: (dept,year),(dept,NULL),(NULL,year),(NULL,NULL)

-- GROUPING SETS: explicit combinations (PostgreSQL)
GROUP BY GROUPING SETS ((dept_id, year), (dept_id), ())

Subqueries & EXISTS

Types of Subqueries

TypeReturnsUsed With
Scalar SubquerySingle value (1 row, 1 col)=, >, <, etc.
Row SubquerySingle row, multiple cols= (row_constructor)
Column SubqueryMultiple rows, 1 columnIN, ANY, ALL, EXISTS
Table SubqueryMultiple rows & columnsFROM (derived table)
Correlated SubqueryDepends on outer queryWHERE with outer ref
 
-- Scalar subquery: students with above-average GPA
SELECT name, gpa
FROM   students
WHERE  gpa > (SELECT AVG(gpa) FROM students);

-- IN subquery: students enrolled in any CS course
SELECT name
FROM   students
WHERE  student_id IN (
    SELECT student_id
    FROM   enrollment e
    JOIN   courses c ON e.course_id = c.course_id
    WHERE  c.dept = 'CS'
);

-- EXISTS: faster than IN for large datasets
SELECT name
FROM   students s
WHERE  EXISTS (
    SELECT 1
    FROM   enrollment e
    WHERE  e.student_id = s.student_id  -- correlated!
);

-- NOT EXISTS: students with no enrollments
SELECT name
FROM   students s
WHERE  NOT EXISTS (
    SELECT 1 FROM enrollment WHERE student_id = s.student_id
);

-- ANY / ALL
SELECT name FROM students
WHERE  gpa > ANY  (SELECT gpa FROM honor_roll); -- > at least one

SELECT name FROM students
WHERE  gpa > ALL  (SELECT gpa FROM honor_roll); -- > every single one

-- Derived table (subquery in FROM)
SELECT dept_id, avg_gpa
FROM  (SELECT dept_id, AVG(gpa) AS avg_gpa
       FROM   students
       GROUP BY dept_id) AS dept_avg
WHERE  avg_gpa > 3.0;
✅
EXISTS vs IN: Use EXISTS when the subquery returns large result sets (stops at first match). Use IN for small, fixed lists. EXISTS is correlated; IN is not (usually).

Window Functions

Window functions compute across a "window" of rows related to the current row — without collapsing rows like GROUP BY does.

function_name() OVER (
    [PARTITION BY col1]   -- like GROUP BY but rows stay
    [ORDER BY col2]       -- defines ordering in window
    [ROWS/RANGE BETWEEN ... AND ...] -- frame clause
)

Ranking Functions

SELECT
    name, dept_id, salary,
    ROW_NUMBER()  OVER (PARTITION BY dept_id ORDER BY salary DESC) AS row_num,
    RANK()        OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk,
    DENSE_RANK()  OVER (PARTITION BY dept_id ORDER BY salary DESC) AS drnk,
    NTILE(4)      OVER (PARTITION BY dept_id ORDER BY salary DESC) AS quartile
FROM employees;
FunctionTies?Example (90,90,80)
ROW_NUMBER()Unique — ties get different numbers1, 2, 3
RANK()Gaps after ties1, 1, 3
DENSE_RANK()No gaps1, 1, 2
NTILE(n)Divides into n bucketsNTILE(2) → 1,1,2

Offset Functions

SELECT
    name, salary,
    LAG(salary, 1, 0)  OVER (ORDER BY hire_date) AS prev_salary,
    LEAD(salary, 1, 0) OVER (ORDER BY hire_date) AS next_salary,
    FIRST_VALUE(salary) OVER (PARTITION BY dept_id ORDER BY salary DESC) AS highest,
    LAST_VALUE(salary)  OVER (PARTITION BY dept_id ORDER BY salary DESC
                          ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING) AS lowest
FROM employees;

Aggregate Window Functions

SELECT
    name, dept_id, salary,
    SUM(salary)   OVER (PARTITION BY dept_id) AS dept_total,
    AVG(salary)   OVER (PARTITION BY dept_id) AS dept_avg,
    SUM(salary)   OVER (PARTITION BY dept_id
                        ORDER BY hire_date
                        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
                       ) AS running_total,
    salary * 100.0 / SUM(salary) OVER (PARTITION BY dept_id) AS pct_of_dept
FROM employees;

Percentile / Distribution

SELECT
    name, salary,
    PERCENT_RANK() OVER (ORDER BY salary) AS pct_rank,  -- 0 to 1
    CUME_DIST()    OVER (ORDER BY salary) AS cum_dist   -- cumulative %
FROM employees;

Classic Window Function Problem: Top N per Group

-- Top 3 earners per department
SELECT * FROM (
    SELECT
        name, dept_id, salary,
        DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dr
    FROM employees
) ranked
WHERE dr <= 3;

Views, CTEs & Derived Tables

Views

A View is a virtual table based on a SELECT query. It's stored as a named query — not data.

-- Create view
CREATE VIEW cs_students AS
SELECT s.name, s.gpa, d.dept_name
FROM   students s
JOIN   departments d ON s.dept_id = d.dept_id
WHERE  d.dept_name = 'Computer Science';

-- Query the view like a table
SELECT * FROM cs_students WHERE gpa > 3.5;

-- Update view (with restrictions)
CREATE OR REPLACE VIEW cs_students AS ...;

-- Drop view
DROP VIEW cs_students;

-- Materialized View (PostgreSQL) - stores actual data
CREATE MATERIALIZED VIEW dept_summary AS
SELECT dept_id, COUNT(*), AVG(gpa)
FROM   students
GROUP BY dept_id;

REFRESH MATERIALIZED VIEW dept_summary;

CTEs — Common Table Expressions

CTEs create temporary named result sets using WITH. More readable than nested subqueries.

-- Basic CTE
WITH dept_avg AS (
    SELECT dept_id, AVG(gpa) AS avg_gpa
    FROM   students
    GROUP BY dept_id
)
SELECT s.name, s.gpa, da.avg_gpa
FROM   students s
JOIN   dept_avg da ON s.dept_id = da.dept_id
WHERE  s.gpa > da.avg_gpa;

-- Multiple CTEs
WITH
  honors AS (SELECT * FROM students WHERE gpa >= 3.7),
  cs_dept AS (SELECT dept_id FROM departments WHERE dept_name = 'CS')
SELECT h.name
FROM   honors h
JOIN   cs_dept c ON h.dept_id = c.dept_id;

-- Recursive CTE: org hierarchy
WITH RECURSIVE org_tree AS (
    -- Anchor: top-level employees
    SELECT emp_id, name, manager_id, 0 AS level
    FROM   employees
    WHERE  manager_id IS NULL
    UNION ALL
    -- Recursive: each employee + their manager
    SELECT e.emp_id, e.name, e.manager_id, ot.level + 1
    FROM   employees e
    JOIN   org_tree ot ON e.manager_id = ot.emp_id
)
SELECT * FROM org_tree;

Indexes & Query Optimization

An index is a data structure that speeds up data retrieval at the cost of additional storage and slower writes.

Index Types

Normalization — 1NF to BCNF

Normalization eliminates redundancy and prevents anomalies: insertion, update, and deletion anomalies.

Functional Dependency (FD)

X → Y means: knowing X uniquely determines Y. If two tuples have the same X, they must have the same Y.

FD TypeDescription
Full FDY depends on ALL of X (not a subset)
Partial FDY depends on a subset of X (X is composite key)
Transitive FDX→Y and Y→Z, so X→Z (via non-key attribute)
Trivial FDY is subset of X (always holds: {A,B}→A)

Armstrong's Axioms

Reflexivity
If Y ⊆ X, then X → Y (trivial FDs)
Augmentation
If X → Y, then XZ → YZ
Transitivity
If X → Y and Y → Z, then X → Z
Union
If X→Y and X→Z then X→YZ
Decomposition
If X→YZ then X→Y and X→Z
Pseudo-transitivity
If X→Y and WY→Z then WX→Z

Normal Forms

1NF
First Normal Form
Rule: All attributes must be atomic (no repeating groups, no multi-valued columns).
Violation: Phone column has "9999, 8888" in one cell.
Fix: Separate row for each phone number.
2NF
Second Normal Form
Rule: Must be 1NF + No partial dependencies (every non-key attribute must fully depend on the whole PK).
Violation: Table(StudentID, CourseID, StudentName, Grade). StudentName depends only on StudentID.
Fix: Separate into Student(StudentID, StudentName) and Enrollment(StudentID, CourseID, Grade).
3NF
Third Normal Form
Rule: Must be 2NF + No transitive dependencies (non-key attributes must not depend on other non-key attributes).
Violation: Table(EmpID, DeptID, DeptName). DeptID→DeptName (transitive via DeptID).
Fix: Separate into Emp(EmpID, DeptID) and Dept(DeptID, DeptName).
BCNF
Boyce-Codd Normal Form (3.5NF)
Rule: Must be 3NF + For every FD X→Y, X must be a superkey.
Stricter than 3NF — handles cases where there are multiple overlapping candidate keys.
Violation: (Student, Subject) → Teacher; Teacher → Subject. Teacher is not a superkey.
Fix: Decompose so Teacher→Subject is in its own table.
4NF
Fourth Normal Form
Rule: Must be BCNF + No multi-valued dependencies.
A→→B means A determines a set of B values independently of other attributes.
💡
Decomposition Properties:
• Lossless Join: Natural join of decomposed tables gives back the original (no spurious tuples).
• Dependency Preserving: All FDs can be checked in decomposed tables without joining. BCNF may not always be DP; 3NF always is.

Denormalization

Sometimes we intentionally break normal forms for performance. Pre-joining data avoids expensive JOIN operations in read-heavy systems (like data warehouses and analytics).

Transactions & ACID Properties

A Transaction is a sequence of database operations treated as a single logical unit of work.

ACID Properties

PropertyMeaningExample
AtomicityAll or nothing. If any step fails, entire transaction is rolled back.Bank transfer: debit and credit must both succeed or both fail.
ConsistencyDatabase moves from one valid state to another. All constraints must hold.Total money before = total money after transfer.
IsolationConcurrent transactions don't interfere. Each sees a consistent view.Two users booking the last seat see it available, only one succeeds.
DurabilityOnce committed, changes persist even after crashes (written to disk/WAL).Committed transaction survives power failure.

Transaction Control

-- Begin transaction explicitly
START TRANSACTION;   -- MySQL
BEGIN;                -- PostgreSQL

UPDATE accounts SET balance = balance - 500 WHERE acc_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE acc_id = 2;

-- Save progress (partial rollback possible)
SAVEPOINT mid_transfer;

UPDATE audit_log SET ...;

-- Rollback to savepoint (undo after savepoint)
ROLLBACK TO SAVEPOINT mid_transfer;

-- Commit: make permanent
COMMIT;

-- Rollback: undo entire transaction
ROLLBACK;

Read Anomalies

Dirty Read
T2 reads data written by T1 which hasn't committed yet. T1 rolls back → T2 read invalid data.
Non-Repeatable Read
T1 reads a row, T2 updates and commits it, T1 reads the same row again → different value!
Phantom Read
T1 queries rows matching a condition, T2 inserts new matching rows, T1 re-runs query → sees "ghost" rows.
Lost Update
T1 and T2 both read X=100, T1 writes 90, T2 writes 80 → T1's update is lost.

START TRANSACTION;

Concurrency Control

Locking

Lock TypeAliasAllows Concurrent Reads?Allows Concurrent Writes?
Shared Lock (S)Read Lock✅ Yes❌ No
Exclusive Lock (X)Write Lock❌ No❌ No
Intent Shared (IS)—✅ Yes✅ Yes
Intent Exclusive (IX)—✅ Yes✅ Yes (same intent)

Two-Phase Locking (2PL)

Growing Phase
Transaction acquires locks. Can acquire new locks but not release any.
Shrinking Phase
Transaction releases locks. Cannot acquire new locks. Begins after first release.
💡
2PL guarantees serializability but can cause deadlocks. Strict 2PL holds all exclusive locks until commit/abort (prevents cascading rollbacks).

Deadlock

T1 holds lock on A, waits for B. T2 holds lock on B, waits for A → circular wait.

Detection
Wait-for graph: detect cycles → abort one transaction (victim)
Prevention
Wait-Die or Wound-Wait protocols based on timestamps
Avoidance
Resource ordering: all transactions lock resources in same order
Timeout
Abort transaction if it waits too long

MVCC — Multi-Version Concurrency Control

Used by PostgreSQL, MySQL InnoDB. Instead of locking, keep multiple versions of a row. Readers don't block writers; writers don't block readers. Each transaction sees a consistent snapshot.

Serializability

A schedule is serializable if it produces the same result as some serial (sequential) execution of the transactions. This is the gold standard for correctness.

Conflict Serializability
Check if the precedence graph (conflict graph) has no cycles. If acyclic → conflict serializable.
View Serializability
Broader than conflict serializability. Two schedules are view equivalent if they read and write the same values.
-- Lock explicitly in SQL
SELECT * FROM accounts WHERE acc_id = 1 FOR UPDATE;  -- exclusive lock
SELECT * FROM accounts WHERE acc_id = 1 FOR SHARE;   -- shared lock (PostgreSQL)
SELECT * FROM accounts WHERE acc_id = 1 LOCK IN SHARE MODE;  -- MySQL

Stored Procedures

DELIMITER //

CREATE PROCEDURE enroll_student (
    IN  p_student_id INT,
    IN  p_course_id  INT,
    OUT p_result     VARCHAR(50)
)
BEGIN
    DECLARE v_count INT;

    SELECT COUNT(*) INTO v_count
    FROM   enrollment
    WHERE  student_id = p_student_id AND course_id = p_course_id;

    IF v_count > 0 THEN
        SET p_result = 'Already enrolled';
    ELSE
        INSERT INTO enrollment (student_id, course_id)
        VALUES (p_student_id, p_course_id);
        SET p_result = 'Enrolled successfully';
    END IF;
END//

DELIMITER ;

-- Call procedure
CALL enroll_student(1, 5, @result);
SELECT @result;

Hashing in DBMS

Static Hashing
Fixed number of buckets. Hash(key) % n → bucket. Problem: overflow as data grows.
Dynamic Hashing (Extendible)
Buckets split as data grows. Directory doubles. No overflow issue. Used in modern systems.

Recovery Techniques

Write-Ahead Logging (WAL)
Log changes BEFORE writing to disk. Standard in PostgreSQL, MySQL.
Checkpointing
Periodically write all dirty pages to disk + log checkpoint. Reduces recovery time.
REDO
Replay committed transactions after crash to ensure durability.
UNDO
Roll back uncommitted transactions after crash to ensure atomicity.
✅
ARIES Recovery Algorithm: Analysis phase → REDO phase → UNDO phase. Used by most modern DBMS (DB2, SQL Server).
